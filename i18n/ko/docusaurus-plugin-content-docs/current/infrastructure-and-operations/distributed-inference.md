# 분산 추론(distributed inference)

분산 추론(distributed inference)은 추론 연산을 서로 연결된 여러 머신에 나누어 AI
시스템이 프로덕션 워크로드를 처리하는 방식을 개선합니다. 모든 요청을 서버 하나로
몰아넣는 대신 여러 워커를 조율하므로, 특정 장치 하나가 병목이 되지 않습니다.

이 방식을 사용하면 트래픽이 늘어나도 추론 시스템을 원활하게 확장할 수 있고, 개별
구성 요소에 장애가 생겨도 안정적으로 동작하며, 지연 시간, 처리량, 자원 사용량을
명확하게 파악할 수 있습니다.

## 분산 추론의 이해 {#understanding-distributed-inference}

어떤 관점에서 보느냐에 따라 분산 추론은 시스템의 서로 다른 계층을 가리킬 수
있습니다.

### 전역 분산 추론 아키텍처 {#global-distributed-inference-architecture}

거시적인 수준에서 분산 추론은 상위 수준의 배포 및 토폴로지 결정을 뜻합니다.

- 모델 하나 또는 그 모델의 여러 레플리카를 여러 지리적 리전에서 실행
- 하드웨어 사양이 서로 다른 이기종 GPU 클러스터에서 트래픽 서빙
- [여러 클라우드(또는 NeoCloud) 공급자](/infrastructure-and-operations/multi-cloud-and-cross-region-inference/)와
  [온프레미스 데이터 센터](/getting-started/on-prem-llms/)에 걸쳐 추론 조율

이 수준에서 팀은 지연 시간을 줄이고, 데이터 상주(data residency) 요구 사항을
충족하고, 내결함성을 높이거나, 특정 리전의 더 저렴하거나 확보하기 쉬운 GPU
용량을 활용하려고 추론을 지리적으로 분산합니다.

이상적으로는 분산 추론 시스템이 이 모든 컴퓨팅 자원을 하나의 논리적 서빙
계층으로 다룹니다. 들어오는 트래픽은 지연 시간, 현재 부하, 비용, GPU 가용성 같은
요소를 바탕으로 가장 적합한 위치로 라우팅됩니다. 따라서 사용자 경험을 해치지
않으면서 멀티 리전 라우팅, 매끄러운 장애 조치(failover), 탄력적인 확장을 구현할
수 있습니다.

거시적 수준의 분산 추론은 주로 추론이 어디에서 실행되는지에 관한 것입니다. 즉
위치, GPU 조달, 대규모 장애 도메인이 핵심입니다.

### 추론 병렬화와 런타임 최적화 {#inference-parallelism-and-runtime-optimizations}

미시적인 수준에서 분산 추론은 단일 추론 요청이나 요청 배치의 작업을 여러 워커,
노드, GPU에 나누는 저수준 최적화 기법을 뜻합니다.

이 기법들은 추론 자체의 내부 동작을 병렬화하는 데 초점을 맞추며, 최근 대규모 LLM
서빙에서 이뤄진 효율 향상 대부분을 이끌어 왔습니다.

대표적인 예는 다음과 같습니다.

- [프리필-디코드 분리](/inference-optimization/prefill-decode-disaggregation/).
  프리필 작업과 디코드 작업을 분리해 각 단계를 특화된 하드웨어에서 실행할 수
  있게 합니다.
- [KV 캐시 오프로딩](/inference-optimization/kv-cache-offloading/). KV 캐시
  데이터를 CPU 메모리나 원격 스토리지로 옮겨 GPU 메모리 부담과 연산 비용을
  줄입니다.
- [추론 라우팅](/inference-optimization/inference-routing/). 유용한 캐시를 갖고
  있거나 용량이 충분한 워커로 요청을 보내 재계산을 줄이고 처리량을 높입니다.
- [병렬화](/inference-optimization/data-tensor-pipeline-expert-hybrid-parallelism/).
  큰 모델이 GPU 하나에 들어가지 않을 때 모델을 여러 GPU에 나눕니다. 단일 노드
  멀티 GPU, 멀티 노드 멀티 GPU 등 여러 형태가 있습니다.

미시적 수준의 분산 추론은 인프라가 어디에 배포되었는지와 관계없이, 주로 추론을
어떻게 효율적으로 실행하는지에 관한 것입니다.

## 분산 추론을 실행해야 하는 이유는 무엇인가요? {#why-should-you-run-distributed-inference}

모델이 커지고 트래픽을 예측하기 어려워지면서, 추론 분산은 단순한 최적화가 아니라
현실적인 필수 요건이 됩니다.

다음은 팀이 프로덕션 시스템에 분산 추론을 도입하는 주요 이유입니다.

### GPU 하나나 머신 한 대의 한계를 넘는 확장 {#scale-beyond-a-single-gpu-or-machine}

GPU 하나는 처리량, 메모리, 동시성에 명확한 한계가 있습니다. 분산 추론을 사용하면
모든 트래픽을 장치 하나로 처리하는 대신 워커를 추가해 시스템을 수평으로 확장할
수 있습니다.

이는 특히 다음과 같은 경우에 중요합니다.

- 동시에 실행되는 채팅 또는 에이전트 워크로드
- 높은 처리량이 필요한 배치 추론 파이프라인
- 컨텍스트 윈도우가 길고 KV 캐시가 큰 모델

고정된 상한에 부딪히는 대신, 인프라와 함께 용량이 늘어납니다.

### GPU 하나에 들어가지 않는 더 큰 모델 서빙 {#serve-larger-models-that-dont-fit-on-one-gpu}

최신 LLM 중 상당수는 양자화를 적용해도 GPU 하나의 메모리 용량을 넘어서며, KV
캐시 증가까지 고려하면 더욱 그렇습니다. 모델 매개변수 수가 늘어날수록 추론에
필요한 메모리와 연산량도 늘어납니다.

분산 추론을 사용하면 이런 모델을 여러 GPU나 여러 노드에 나누어 서빙할 수
있습니다. 덕분에 팀은 더 큰 모델을 실행하고, 더 긴 컨텍스트를 지원하고, 그렇지
않으면 프로덕션 배포를 불가능하게 만들 메모리 부족(out-of-memory) 오류를 피할 수
있습니다.

### 신뢰성과 내결함성 향상 {#increase-reliability-and-fault-tolerance}

프로덕션 추론 시스템은 장애를 견뎌야 합니다. GPU는 멈추고, 노드는 오프라인이
되며, 리전 전체를 사용할 수 없게 되기도 합니다. 분산 추론을 사용하면 다음이
가능합니다.

- 워커에 장애가 나면 트래픽을 자동으로 다른 곳으로 라우팅
- 리전 장애가 발생해도 전체 서비스가 중단되지 않음
- 장애 상황에서 용량을 동적으로 재분배

그 결과 추론은 취약한 단일 장애 지점에서 탄력적인 프로덕션급 서비스로 바뀝니다.

### 더 현명한 자원 활용을 통한 비용 절감 {#reduce-costs-through-smarter-resource-usage}

분산 추론을 사용하면 성능을 희생하지 않고 비용을 최적화할 수 있습니다. 강력한
머신 한 대를 과도하게 프로비저닝하는 대신, 팀은 자원을 더 정밀하게 할당할 수
있습니다.

대표적인 비용 절감 전략은 다음과 같습니다.

- 추론 워크로드에 따라 서로 다른 GPU 유형을 섞어서 사용
- 사용량이 적은 시간대에 용량 축소
- 더 저렴한 리전이나 공급자로 트래픽 라우팅
- KV 캐시처럼 메모리를 많이 쓰는 구성 요소를 오프로드

그 결과 GPU 사용률은 높아지고 요청당 비용은 낮아집니다.

---

일반적으로 다음과 같은 경우에 분산 추론이 필요합니다.

- 트래픽을 예측하기 어렵거나 급증이 잦은 경우
- 모델이 크거나 메모리를 많이 사용하는 경우
- 가동 시간과 지연 시간이 중요한 경우
- GPU 비용과 사용률을 적극적으로 최적화해야 하는 경우

이 시점에서는 서버 한 대를 수직으로 확장하는 것만으로는 충분하지 않습니다. 분산
추론이 서빙 아키텍처의 기반이 됩니다.

## 분산 추론의 과제 {#challenges-of-distributed-inference}

단일 노드 배포를 넘어서기 전에 다음과 같은 트레이드오프를 이해해 두어야 합니다.

### 네트워크 통신 오버헤드 {#network-communication-overhead}

분산 추론은 워커, GPU, 노드 사이의 잦은 통신에 의존합니다. 모델 샤딩,
프리필-디코드 분리, KV 캐시 이동, 노드 간 조율은 모두 네트워크 오버헤드를
일으킵니다.

이로 인해 다음과 같은 문제가 생길 수 있습니다.

- GPU 간 또는 노드 간 통신으로 인한 종단 간 지연 시간 증가
- 네트워크 대역폭과 지터(jitter)에 대한 민감도 증가
- 인터커넥트가 느리거나 불안정할 때의 성능 저하

추론이 더 분산될수록 순수 연산보다 네트워크가 병목이 되곤 합니다.

### 구축 및 운영 복잡성 {#build-and-operational-complexity}

분산 시스템은 본질적으로 단일 노드 구성보다 구축하고 운영하기가 복잡합니다. 팀은
오케스트레이션, 오토스케일링, 라우팅, 상태 점검(health check), 관측 가능성 등
움직이는 여러 요소를 관리해야 합니다.

대표적인 과제는 다음과 같습니다.

- 여러 클러스터나 리전에 걸친 배포 조율
- 환경 간 구성 편차(configuration drift) 관리
- 확장 이벤트 중에도 일관된 동작 보장

강력한 도구와 전문 지식이 없으면 운영 복잡성이 성능 향상을 금세 넘어설 수
있습니다.

### 통합 관측 가능성과 비용 가시성 {#unified-observability-and-cost-visibility}

추론이 여러 워커, GPU, 클러스터, 리전으로 퍼질수록 시스템 동작을 통합된 시각으로
파악하기가 훨씬 어려워집니다.

팀은 흔히 다음과 같은 문제를 겪습니다.

- 분산된 구성 요소 전반에서 지연 시간, 처리량, 오류를 연관 지어 분석하기
- 전체 수준에서 GPU 사용률과 메모리 부담 파악하기
- 특정 모델, 워크로드, 테넌트에 비용 귀속시키기
- 유휴 GPU나 불균형한 트래픽 같은 비효율 찾아내기

[중앙화된 관측 가능성](/infrastructure-and-operations/comprehensive-observability/)과
비용 가시성이 없으면 분산 추론 시스템은 불투명해질 수 있습니다. 그러면 성능을
최적화하고 문제를 해결하기가 어려워집니다.

### 상태 관리와 일관성 {#state-management-and-consistency}

많은 추론 워크로드는 상태를 가집니다. 채팅 세션, 에이전트 워크플로, 스트리밍
응답, KV 캐시 재사용은 모두 요청 간에 상태를 유지하는 데 의존합니다.

분산 환경에서는 다음과 같은 질문이 생깁니다.

- 세션 상태나 KV 캐시를 어디에 두어야 하는가
- 워커 간에 상태를 어떻게 공유, 복제, 이전하는가
- 중요한 상태를 가진 워커에 장애가 나면 어떻게 되는가

상태 관리가 부실하면 재계산, 캐시 미스, 지연 시간 악화로 이어질 수 있습니다.

## 분산 추론 시스템의 설계와 운영 {#designing-and-running-a-distributed-inference-system}

분산 추론 시스템을 구축하는 일은 GPU를 더 추가하는 것으로 끝나지 않습니다.
이기종 자원으로 이뤄진 전체 플릿(fleet)에 걸쳐 연산을 조율하고, 작업을
지능적으로 스케줄링하고, 상태를 관리하고, 트래픽을 효율적으로 라우팅해야 합니다.

크게 보면 프로덕션급 분산 추론 시스템에는 다음 구성 요소가 필요합니다.

### 지능형 스케줄링과 요청 라우팅 {#intelligent-scheduling-and-request-routing}

분산 추론의 핵심에는 각 요청을 어디에서 실행할지 결정하는 스케줄러가 있습니다.
이 결정은 여러 요소에 따라 달라집니다.

- GPU 가용성과 메모리 부담
- 현재 부하와 큐 깊이
- 프롬프트 길이, 배치 크기, 스트리밍 동작 같은 요청 특성
- KV 캐시 크기와 지역성 같은 캐시된 상태
- 지연 시간 또는 비용 제약

단순한 라운드 로빈 스케줄러는 규모가 커지면 금방 한계를 드러냅니다. 최신 추론
시스템은 처리량과 예측 가능한 지연 시간을 유지하기 위해 상태를 고려하는 동적
스케줄링에 의존합니다.

### 분산 추론 런타임 {#distributed-inference-runtimes}

대부분의 팀은 분산 추론을 처음부터 직접 구축하지 않습니다. 대신 병렬화나
프리픽스 인식 라우팅 같은 핵심 [추론 기법](/inference-optimization/)을 구현한
전문 런타임을 사용합니다.

실제로 팀은 vLLM, SGLang, llm-d 같은 추론 런타임을 Kubernetes에서 실행하는
경우가 많습니다. 이 런타임들은 미시적 수준에서 추론이 실행되는 방식을 어느 정도
처리해 주지만, 멀티 리전 라우팅, 오토스케일링, 운영 가시성 같은 LLM 워크로드의
거시적 수준 문제까지 완전히 해결하지는 못합니다.

### 오케스트레이션, 확장, 관측 가능성 {#orchestration-scaling-and-observability}

프로덕션에서 분산 추론을 실행하려면 팀은 다음 요소도 통합해야 합니다.

- GPU 풀 전반의 오토스케일링 정책
- 상태 점검과 장애 복구
- [지연 시간(예: TTFT와 ITL)](/llm-inference-basics/llm-inference-metrics/),
  처리량, GPU 사용률, 오류에 대한 통합 관측 가능성
- 모델, 리전, 워크로드별 비용 귀속

특히 여러 클러스터나 클라우드에 걸쳐 운영할 때는 이 오케스트레이션 계층에
엔지니어링 노력이 가장 많이 들어가는 경우가 많습니다.

## 모든 것을 직접 구축하는 대신 플랫폼 사용 {#using-a-platform-instead-of-building-everything-yourself}

많은 팀에게 이 모든 계층을 내부에서 구축하고 유지하는 일은 장기적인 운영 부담이
됩니다. 이럴 때 프로덕션 추론 플랫폼이 복잡성을 크게 줄여 줄 수 있습니다.

저희 Inference Platform은 다음 기능을 통합해 분산 추론을 위한 프로덕션 준비
기반을 제공합니다.

- 지능형 요청 라우팅과 스케줄링
- [프리필-디코드 분리](/inference-optimization/prefill-decode-disaggregation/)
  같은 고급 추론 최적화 기법
- 멀티 GPU, 리전 간, 멀티 클라우드 배포
- 오토스케일링, 내결함성, 통합 관측 가능성

시스템은 하나의 일관된 계층으로 관리되고 팀은 모델과 애플리케이션에 집중할 수
