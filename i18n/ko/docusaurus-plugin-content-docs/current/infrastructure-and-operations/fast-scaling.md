# 빠른 스케일링

프로덕션 환경에서 LLM 추론을 실행하는 일은 모델을 학습하는 일과 완전히 다릅니다.
학습은 배치 단위로 진행되어 예측이 가능하지만, 추론은 실시간 사용자 수요에 따라
움직입니다. 이 수요는 갑자기 몰리는 경우가 많고 예측하기 어려우며, 지연 시간이나
다운타임을 용납하지 않습니다.

따라서 시스템은 트래픽이 급증할 때 빠르게 확장하고, 유휴 상태일 때는 비용을
아끼기 위해 0까지 축소해야 합니다. 이런 탄력성은 효율성의 기본입니다.

그런데 많은 조직이 추론을 학습처럼 다루어, 장기 약정으로 고정된 GPU 용량을 미리
확보해 둡니다. 이런 방식은 흔히 다음과 같은 결과로 이어집니다.

- **과잉 프로비저닝**: GPU 용량이 낭비되고 유휴 비용이 높아집니다.
- **과소 프로비저닝**: 요청이 누락되고 지연 시간이 급증하며 사용자 경험이
  나빠집니다.
- **유연하지 않은 예산**: 실제 사용 패턴에 맞춰 조정되지 않는 경직된 지출이
  생깁니다.

## 서버리스가 만능 해결책이 아닌 이유 {#why-serverless-isnt-a-silver-bullet}

스케일링 문제는 서버리스 컴퓨팅이 이미 수년 전에 해결한 익숙한 문제처럼
보입니다. AWS Lambda 같은 플랫폼 덕분에 수요에 맞춰 확장하기가 쉬워졌지만,
서버리스는 AI 워크로드에 잘 맞지 않습니다. 이유는 다음과 같습니다.

- **GPU 미지원**: 대부분의 서버리스 플랫폼은 GPU를 지원하지 않습니다. 이는
  단순한 기술적 누락이 아니라 아키텍처와 실무상의 고려 사항에서 비롯된
  결과입니다.
- **GPU는 쉽게 나눠 쓸 수 없음**: GPU는 강력하고 병렬성이 높지만, 서로 다른
  모델의 많은 추론 작업을 동시에 처리하는 데에는 CPU만큼 유연하지 않습니다.
- **유휴 GPU의 높은 비용**: GPU는 컴퓨팅 세계의 고성능 스포츠카와 같습니다. 특정
  작업에서는 뛰어나지만 유지 비용이 많이 들며, 쉬지 않고 사용하지 않으면 더욱
  그렇습니다.

## 콜드 스타트 문제 {#the-cold-start-problem}

추론 워크로드에는 빠르게 확장하고, 비용을 관리하며, 성능을 유지할 수 있는
인프라가 필요합니다. 스케일링의 근본적인 과제 중 하나는 콜드 스타트(cold
start)입니다.

컨테이너로 LLM을 배포하는 맥락에서 콜드 스타트는 Kubernetes 노드가 해당 배포를
한 번도 실행한 적이 없을 때 발생합니다. 그 결과 컨테이너 이미지가 로컬에
캐시되어 있지 않으므로, 모든 이미지 레이어를 처음부터 가져와 초기화해야 합니다.

이 문제는 세 단계에서 나타납니다.

1. **클라우드 프로비저닝**: 클라우드 공급자가 새 인스턴스를 할당하고 Kubernetes
   클러스터에 연결하는 데 걸리는 시간입니다. 인스턴스 유형과 가용성에 따라
   30초에서 몇 분까지 걸리며, NVIDIA A100이나 H100처럼 수요가 많은 GPU라면 몇
   시간이 걸리기도 합니다.
2. **컨테이너 이미지 가져오기**: LLM 이미지는 수많은 의존성과 커스텀 라이브러리
   때문에 일반적인 Python 작업 이미지보다 훨씬 크고 복잡합니다. 클라우드
   공급자는 수 기가비트 대역폭을 내세우지만, 실제 이미지 다운로드 속도는 그보다
   훨씬 느린 경우가 많습니다. 그 결과 이미지를 가져오는 데 3~5분이 걸릴 수
   있습니다.
3. **모델 로딩**. 모델을 로드하는 데 걸리는 시간은 모델 크기에 크게 좌우됩니다.
   LLM은 수십억 개의 매개변수 때문에 상당한 지연을 일으킵니다. 주요 병목은
   다음과 같습니다.

   - **모델 허브에서의 느린 다운로드**: Hugging Face 같은 플랫폼은 고처리량
     멀티파트 다운로드에 최적화되어 있지 않아, 대용량 모델 파일을 가져오는 데
     시간이 오래 걸립니다.
   - **순차적인 데이터 흐름**: 모델 파일은
     **원격 스토리지 → 로컬 디스크 → 메모리 → GPU**의 여러 단계를 거쳐
     전송됩니다. 이 단계들 사이에는 병렬화가 거의 또는 전혀 없습니다. 단계마다
     지연 시간이 더해지며, 캐시하거나 스트리밍하기 어려운 대용량 파일에서 특히
     그렇습니다.
   - **온디맨드 스트리밍 부재**: 추론을 시작하기 전에 모델 파일을 모두
     다운로드해 디스크에 기록해야 합니다. 이 때문에 I/O 작업이 추가로 발생하고
     시작이 늦어집니다.

콜드 스타트 문제의 각 단계마다 지연을 최소화하기 위한 별도의 전략이 필요합니다.

## 스케일링 지표 {#scaling-metrics}

LLM 추론 인프라를 확장하려면 시스템 부하에 단순히 반응하는 것 이상이 필요합니다.
반응성이 좋고 효율적이며 비용 효율적인 스케일링을 달성하려면 올바른 지표 선택이
중요합니다.

- **CPU 사용률**. 단순하고 임계값이 명확하지만, Python 기반 워크로드의 실제
  부하를 반영하지 못합니다. GIL(Global Interpreter Lock)은 특히 멀티코어
  머신에서 CPU 병렬성을 제한하므로, 이 지표는 스케일링 결정을 잘못 이끌 수
  있습니다.
- **GPU 사용률**. 이론적으로는 더 타당한 지표이지만 실제로는 정확하지 않습니다.
  `nvml` 같은 도구는 샘플링 구간 동안 커널이 잠깐이라도 실행되면 GPU를 "사용
  중"으로 보고합니다. 이 방식은 배칭이나 실제 처리량을 고려하지 않으므로, 너무
  이른 확장이나 용량에 대한 잘못된 확신으로 이어집니다.
- **QPS(초당 쿼리 수)**. 전통적인 웹 서비스에서 널리 쓰이지만 LLM 추론에서는 덜
  유용합니다. 생성 요청은 입력 길이와 생성되는 토큰 수에 따라 크기와 연산 비용이
  크게 달라집니다. 그 결과 QPS는 일관성이 부족하고 오토스케일링에 맞게 조정하기
  어렵습니다.
- **동시성**. 대기 중이거나 처리 중인 활성 요청의 수를 나타내는 이 지표는 시스템
  부하를 반영하는 데 이상적입니다. 동시성은 배치 크기를 기준으로 쉽게 설정할 수
  있고 실제 시스템 수요와 직접적인 상관관계가 있어 정밀한 스케일링이 가능합니다.
  다만 동시성이 제대로 작동하려면, 동시성을 지표로 자동 계측하고 이를 배포
  플랫폼의 스케일링 신호로 제공하는 서비스 프레임워크의 지원이 필요합니다.
