# 다중 모델 추론 파이프라인

다중 모델 추론 파이프라인(multi-model inference pipeline)은 여러 모델이 함께
동작해 하나의 결과를 만들어 내는 시스템입니다. 하나의 모델에 모든 일을 맡기는
대신, 작업을 여러 단계로 나눕니다. 각 단계는 검색, OCR, 분류, 생성, 후처리처럼
특정한 작업 하나에 집중합니다.

이는 하나의 엔드포인트 뒤에서 모델 하나를 실행하는 방식과 다릅니다. 하나의
모델을 여러 장치에 나누어 올리는
[파이프라인 병렬화](/inference-optimization/data-tensor-pipeline-expert-hybrid-parallelism/)와도
다릅니다. 여기서 핵심 질문은 모델 하나를 어떻게 분산하느냐가 아닙니다. 여러
모델이 하나의 요청 경로 안에서 협력하는 시스템을 어떻게 설계하고, 배포하고,
운영하느냐입니다.

## 다중 모델 파이프라인의 형태 {#what-a-multi-model-pipeline-looks-like}

가장 단순하게는 파이프라인으로 떠올릴 수 있습니다. 하지만 실제 시스템 중
상당수는 일직선보다는 추론 그래프(inference graph)에 더 가깝습니다. 어떤 단계는
병렬로 실행됩니다. 어떤 요청은 서로 다른 후속 경로로 갈라집니다. 어떤 단계는
선택 사항입니다.

패턴마다 트레이드오프가 다릅니다.

다음 절에서 각 패턴을 더 자세히 설명합니다.

### 순차 파이프라인 {#sequential-pipelines}

가장 직관적인 구성입니다. 각 단계의 출력이 다음 단계의 입력이 됩니다.

```text
Input → Stage A → Stage B → Stage C → Output
```

순차 파이프라인은 개념적으로 단순하지만, 단계별 지연 시간이 누적됩니다. 단계마다
50 ms가 걸린다면, 네 단계만으로도 최종 생성 단계가 시작되기 전에 종단 간 지연
시간이 수백 밀리초에 이를 수 있습니다.

### 병렬 팬아웃 / 팬인 {#parallel-fan-out--fan-in}

이 패턴에서는 하나의 요청을 여러 모델에 동시에 보냅니다. 그런 다음 각 모델의
출력을 병합하거나, 투표로 정하거나, 점수를 매깁니다.

예시는 다음과 같습니다.

- 앙상블 예측
- 여러 후보 생성기를 실행하고 가장 좋은 결과를 선택하기
- 같은 이미지에 객체 탐지와 분할(segmentation)을 함께 적용하기

병렬 팬아웃(fan-out)은 품질이나 커버리지를 높일 수 있지만, 전체 연산 사용량이
늘어납니다. 지연 시간은 적정 수준에 머물더라도 요청당 비용은 빠르게 오를 수
있습니다.

### 조건부 라우팅 {#conditional-routing}

이 패턴에서는 앞 단계가 다음에 무엇을 할지 결정합니다.

예시는 다음과 같습니다.

- 작은 분류기가 어려운 요청만 더 큰 모델로 보내기
- 언어 감지기가 적절한 후속 모델을 고르기
- 안전 필터가 안전하지 않은 입력을 차단하거나 다른 경로로 보내기

이 방식은 비용을 줄이고 지연 시간을 지킬 수 있지만, 라우터가 신뢰할 수 있어야만
효과가 있습니다. [RouteLLM](https://arxiv.org/abs/2406.18665) 연구에서는 더 강한
LLM과 더 약한 LLM 중 하나를 고르도록 학습된 라우터가 일부 경우 응답 품질을
떨어뜨리지 않고 비용을 2배 이상 줄였습니다. 반면 앞 단계에서 잘못 판단하면
요청이 엉뚱한 경로로 가서 품질이 떨어질 수 있습니다. 더 많은 라우팅 전략은
[추론 라우팅](/inference-optimization/inference-routing/)을 참고하세요.

### 멀티모달 파이프라인 {#multimodal-pipelines}

이러한 시스템은 서로 다른 데이터 유형을 다루므로 서로 다른 유형의 모델을 함께
씁니다.

예시는 다음과 같습니다.

- 이미지 인코더 → 언어 모델
- 음성 모델 → 언어 모델 → 모더레이션 모델
- 문서 파서 → 표 추출기 → 언어 모델

여기서 핵심 과제는 대개 모델 품질만이 아닙니다. 병목을 만들거나 깨지기 쉬운
인터페이스를 만들지 않고 단계 사이의 중간 데이터를 어떻게 옮기고
정규화하느냐입니다.

## 다중 모델 파이프라인이 중요한 이유 {#why-multi-model-pipelines-matter}

프로덕션 AI 애플리케이션 중 상당수는 사실 모델 하나로 풀리는 문제가 아닙니다. 큰
모델 하나가 여러 작업을 그럭저럭 잘 해낼 때가 많지만, 그렇다고 해서 각 단계에
가장 적합한 선택이라는 뜻은 아닙니다.

### 작업에 더 잘 맞는 모델 {#better-capability-fit}

모델마다 최적화된 작업이 다릅니다.

- OCR 모델은 노이즈가 많은 이미지나 PDF에서 텍스트를 추출하도록 조정되어
  있습니다.
- 임베딩 모델은 시맨틱 검색에 맞게 조정되어 있습니다.
- 재순위화 모델(reranker)은 관련성 점수 매기기에 맞게 조정되어 있습니다.
- 라우팅, 필터링, 모더레이션에는 더 작은 분류기나 가드 모델로도 충분한 경우가
  많습니다.
- 더 큰 생성 모델은 최종 추론이나 응답 합성에 아껴 두는 것이 가장 좋습니다.

이렇게 역할을 나누는 편이 모델 하나를 모든 단계에 억지로 맞추는 것보다 효과적인
경우가 많습니다.

### 하드웨어에 더 잘 맞는 구성 {#better-hardware-fit}

모든 단계에 같은 하드웨어가 필요한 것은 아닙니다.

가벼운 전처리나 검증 단계는 CPU에서도 잘 실행될 수 있습니다. 비전 인코더,
재순위화 모델, 대형 생성기에는
[고성능 GPU](/getting-started/choosing-the-right-gpu/)가 필요할 수 있습니다.
어떤 단계는 배칭이 잘 되는 반면, 어떤 단계는 지연 시간에 매우 민감해서 작고
빠르게 유지해야 합니다.

덕분에 팀은 가장 비싼 단계에 맞춰 파이프라인 전체를 과잉 프로비저닝하는 대신, 각
단계를 워크로드에 맞는 하드웨어에 배치할 수 있습니다.

### 독립적인 확장 {#independent-scaling}

단계마다 트래픽 특성이 다른 것이 보통입니다. 검색기(retriever)는 실행 비용이
낮지만 모든 요청에서 실행될 수 있고, 대형 생성기는 비싸지만 필터링을 거친 일부
트래픽에서만 실행될 수 있습니다. 각 단계가 독립적으로 배포 가능한 단위라면, 가장
느린 구성 요소에 묶이지 않고 자체 신호(큐 깊이, GPU 사용률, 동시성)에 따라
확장할 수 있습니다.

### 더 낮은 요청당 비용 {#lower-cost-per-request}

다단계 파이프라인은 단일 모델로는 쉽게 얻기 어려운 비용 절감 여지를 만듭니다.

- 저렴한 분류기나 라우터가 어려운 요청만 더 크고 비싼 모델로 보낼 수 있습니다.
- 가벼운 단계는 CPU나 더 작은 GPU에서 실행할 수 있습니다.
- 범위가 좁은 작업(추출, 분류, 모더레이션)에서는 더 작은 전문 모델이 범용 LLM을
  대신할 수 있습니다.

이러한 절감 효과는 파이프라인이 잘 조정되어 있을 때만 나타납니다. 설계가 부실한
파이프라인은 하나의 거대한 단일 모델보다 비용이 더 들기 쉽습니다.

### 더 빠른 반복 개선 {#better-iteration-speed}

다중 모델 시스템은 모듈성이 더 높습니다. 검색 단계의 성능이 부족하면 생성 단계를
바꾸지 않고 검색 단계만 교체하거나 다시 조정할 수 있습니다. 최종 모델이 너무
비싸면 시스템의 나머지 부분을 다시 설계하지 않고도 더 작은 대안을 시험해 볼 수
있습니다. 이렇게 국소적으로 반복 개선할 수 있다는 점은 팀이 단일 서비스 대신
추론 그래프를 채택하는 이유 중 하나입니다.

## 다중 모델 파이프라인을 쓰지 말아야 할 때 {#when-not-to-use-a-multi-model-pipeline}

다중 모델 파이프라인은 과도하게 설계하기 쉽습니다. 모델 하나로 이미 요구 사항을
충족한다면 단순하게 유지하세요. 단계를 추가하는 것은 분명한 가치가 있을 때만
의미가 있습니다.

워크로드를 여러 단계로 나누기 전에 다음을 확인하세요.

- 각 단계가 모델 하나로는 충분히 해결하지 못하는 별개의 문제를 해결하는가?
- 파이프라인이 늘어난 복잡도를 정당화할 만큼 품질, 비용, 제어력을 개선하는가?
- 지연 시간 예산이 추가 홉과 대기 지점을 감당할 수 있는가?
- 모델이 바뀌더라도 단계 사이의 인터페이스를 안정적으로 유지할 수 있는가?
- 독립적인 확장이 실제로 비용을 절약하는가, 아니면 운영 부담만 늘리는가?

모델 조합(model composition)에는 실질적인 비용이 따릅니다.

- 배포할 서비스 증가
- 단계 간 계약 증가
- [관측 가능성](/infrastructure-and-operations/comprehensive-observability/)
  작업 증가
- 장애 유형 증가
- 종단 간 수준의 조정 작업 증가

요구 사항을 충족하는 가장 작은 아키텍처로 시작하고, 확실히 제 몫을 하는 단계만
추가하세요.

## 아키텍처 예시 {#example-architectures}

다음은 다중 모델 추론 파이프라인이 자연스럽게 들어맞는 구체적인 패턴입니다.

### RAG 파이프라인 {#rag-pipeline}

일반적인 RAG 경로는 다음과 같습니다.

```text
Query → Embed → Retrieve → Rerank → Generate → (Optional) Verify
```

각 단계의 역할은 분명합니다.

- 임베딩 모델이 유사한 콘텐츠를 찾습니다
- 검색기가 검색 범위를 좁힙니다
- 재순위화 모델이 관련성을 높입니다
- 생성기가 근거 자료를 응답으로 만듭니다
- 마지막 검증기나 인용 검사기가 환각 위험을 줄입니다

### 문서 AI 파이프라인 {#document-ai-pipeline}

문서 워크플로는 다음과 같을 수 있습니다.

```text
Document image → OCR → Layout extraction → Classify → Summarize → Structured Output
```

정확도, 형식, 추적 가능성이 중요하다면 이 과정을 모델 하나로 대체하기는
어렵습니다. OCR과 레이아웃 추출은 요약과는 매우 다른 작업입니다. 다만 큰 중간
산출물이 여러 단계를 거쳐 이동할 수 있다는 트레이드오프가 있으므로 페이로드
설계가 중요합니다. 출력을 다른 시스템에 바로 넘겨야 한다면
[구조화된 출력](/model-interaction/structured-outputs/)을 쓰면 그 인계 과정을
훨씬 쉽게 유지할 수 있습니다.

### 멀티모달 어시스턴트 {#multimodal-assistant}

멀티모달 애플리케이션은 이미지, 오디오, 텍스트를 각각 별도의 인코더로 보낸 뒤,
후속 언어 모델이 결합된 신호를 사용하도록 할 수 있습니다.

이런 시스템은 하드웨어 전문화를 잘 보여 주는 사례인 경우가 많습니다. 음성 단계,
이미지 단계, 언어 단계는 런타임 특성과 확장 요구가 크게 다를 수 있습니다.

## 단일 모델과 다중 모델 파이프라인 비교 {#single-model-vs-multi-model-pipeline}

어느 쪽이 항상 낫다고 할 수는 없습니다. 모델 하나로 이미 품질, 지연 시간, 비용
목표를 충족한다면 단일 모델을 선택하세요. 전문화된 단계가 추가 지연 시간과 운영
작업을 정당화할 만큼 품질, 비용, 제어력을 분명히 개선한다면 다중 모델
파이프라인을 선택하세요.

| 기준                         | 단일 모델     | 다중 모델 파이프라인 |
|------------------------------|---------------|----------------------|
| 단순성                       | 더 단순함     | 구성 요소가 더 많음  |
| 지연 시간                    | 보통 더 낮음  | 흔히 더 높음         |
| 하드웨어 유연성              | 제한적        | 더 높음              |
| 독립적인 확장                | 제한적        | 더 강력함            |
| 전문화                       | 제한적        | 더 강력함            |
| 운영 부담                    | 더 낮음       | 더 높음              |
| 단일 단계 실험               | 더 어려움     | 더 쉬움              |

경험적으로는 다음과 같이 접근하세요.

- 모델 하나로 이미 제품 요구 사항을 충족한다면 모델 하나로 시작하세요. 여러
  모델을 조합하기로 결정하기 전에
  [적합한 모델을 고르는 방법](/getting-started/choosing-the-right-model/)을 알아
  두세요.
- 단계가 분명히 도움이 될 때 추가하세요
- 단계 수는 가능한 한 적게 유지하세요

## 자주 묻는 질문 {#faqs}

### 복합 AI 시스템이란 무엇인가요? {#what-is-a-compound-ai-system}

Berkeley AI Research(BAIR) 연구진은 복합 AI 시스템(compound AI system)을 여러
모델 호출, 검색기, 외부 도구처럼
[상호작용하는 여러 구성 요소를 사용해 AI 작업을 처리하는](https://bair.berkeley.edu/blog/2024/02/18/compound-ai-systems/)
시스템으로 정의합니다. RAG 애플리케이션, 문서 AI 파이프라인, AI 에이전트는 모두
복합 AI 시스템입니다. 다중 모델 추론 파이프라인은 이러한 구성 요소를
프로덕션에서 실행하는 서빙 레이어입니다.

### 모든 RAG 시스템을 다중 모델 파이프라인으로 다뤄야 하나요? {#should-every-rag-system-be-treated-as-a-multi-model-pipeline}

개념적으로는 그렇습니다. 검색, 재순위화, 생성이 별개의 단계이기 때문입니다.
하지만 운영 측면에서는 항상 그렇지는 않습니다. 어떤 팀은 이러한 단계를 하나의
서비스 경계 뒤에 묶어 하나의 배포 단위로 다룹니다. 추상화가 단순해 보이더라도
단계별 병목은 파악하고 있어야 합니다.

### 모든 단계를 하나의 서비스에 두어야 하나요? {#should-all-stages-live-in-one-service}

항상 그렇지는 않습니다. 서비스를 하나로 두면 홉 지연 시간을 줄이고 로컬 조정을
단순하게 만들 수 있습니다. 단계마다 다른 하드웨어, 확장 정책, 릴리스 주기, 장애
격리가 필요하다면 서비스를 분리하는 편이 낫습니다.

### 다중 모델 파이프라인으로 추론 비용을 낮출 수 있나요? {#can-multi-model-pipelines-lower-inference-cost}

작은 전문 모델이 큰 모델 실행 전에 요청을 걸러내거나 라우팅할 때, 또는 단계마다
더 저렴한 하드웨어를 더 효율적으로 사용할 때 비용을 줄일 수 있습니다. 하지만
파이프라인 설계가 부실하면 오히려 반대 결과가 나오기 쉽습니다.

### 에이전트 워크플로와는 어떻게 다른가요? {#how-is-this-different-from-an-agentic-workflow}

둘 다 여러 모델 호출을 연결하지만, 다중 모델 파이프라인은 미리 설계해 두는,
대체로 고정된 그래프입니다. 에이전트는 어떤 도구나 모델을 몇 번, 어떤 순서로
호출할지 동적으로 결정합니다. 에이전트는 파이프라인 개념의 상위 집합으로,
유연성이 더 크지만 지연 시간과 비용의 변동도 더 큽니다. 어느 쪽이든 단계 간
인터페이스를 예측 가능하게 유지하려면
[함수 호출](/model-interaction/function-calling/)과
[구조화된 출력](/model-interaction/structured-outputs/)이 해결책의 일부가 되는
경우가 많습니다.
