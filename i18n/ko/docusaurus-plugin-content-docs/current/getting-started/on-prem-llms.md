# 온프레미스 LLM 배포

온프레미스 LLM 배포를 택하면 팀이 데이터, 인프라, 비용을 직접 통제할 수
있습니다. GPU와 네트워킹부터 확장과 모니터링까지
[LLM 인프라 스택 전체](/infrastructure-and-operations/what-is-llm-inference-infrastructure/)를
직접 관리합니다. 기업은 보통 사설 데이터 센터나 에어갭(air-gapped) 환경에서 이
패턴을 도입하며, 오픈소스 모델과 함께 쓰는 경우가 많습니다.

이런 자유에는 장점도 있지만 만만치 않은 엔지니어링 과제도 따릅니다.

## 팀이 온프레미스 LLM 배포를 선택하는 이유 {#why-teams-choose-on-prem-llm-deployments}

AI 팀이 온프레미스 배포를 택하는 이유는 보통 다음과 같습니다.

- **데이터 보안과 규정 준수**: 모든 추론이 자체 인프라 안에서 실행됩니다. 덕분에
  민감한 정보가 환경 밖으로 유출될 위험이 줄어듭니다. 의료, 금융, 공공 같은
  산업의 엄격한 규제 요건을 충족하는 데도 도움이 됩니다.
- **예측 가능한 비용**: 초기 하드웨어 투자 이후에는 지속적인 추론 비용이 사용량
  기반 서버리스 API보다 낮아질 수 있습니다. 다만 예산 안에서 운영하려면
  [KV 캐시 오프로딩](/inference-optimization/kv-cache-offloading/)이나
  [프리픽스 캐싱](/inference-optimization/prefix-caching/) 같은 추론 최적화
  기법을 적용해야 할 수도 있습니다.
- **성능 통제**: 공급자의 SLA에 얽매이지 않고 지연 시간, 처리량, 확장 목표에
  맞춰 추론 성능을 직접 튜닝할 수 있습니다. 요청량이 많거나 지연 시간에 민감한
  애플리케이션에서 매우 유용합니다.
- **외부 의존성 감소**: 모든 처리가 자체 네트워크 안에서 이루어지므로 외부
  공급자에 의존할 필요가 없습니다. 인증, 접근 제어, 감사 같은 맞춤형 보안 조치를
  적용할 수 있고, 외부 위협에 노출될 여지를 최소화합니다.

실제로 온프레미스 LLM 배포는 다음과 같은 경우에 가장 적합합니다.

- 워크로드가 지연 시간에 민감하고 엄격한 SLA를 지켜야 하는 경우
- 엄격한 규정 준수 요건 때문에 벤더 클라우드를 선택할 수 없는 경우
- 조직이 인프라와 유지 보수에 드는 투자를 감당할 수 있는 경우

그렇지 않다면 오버헤드가 적은 하이브리드 배포나 클라우드 기반 배포가 더 나은
선택일 수 있습니다.

## 온프레미스 LLM 배포의 과제 {#challenges-of-on-prem-llm-deployments}

온프레미스 솔루션은 유연하지만 그만큼 무거운 책임이 따릅니다. 이점이 오버헤드를
확실히 넘어설 때만 도입할 가치가 있습니다.

주요 과제는 다음과 같습니다.

- **높은 초기 비용**: GPU, 네트워킹 장비, 스토리지에는 큰 자본 투자가 필요하고,
  하드웨어 교체 주기도 비용이 많이 듭니다.
- **운영 복잡성**: 오토스케일링, 업그레이드, 모니터링, GPU 조달을 모두 직접
  책임져야 합니다.
- **느린 반복 속도**: 프런티어 모델, 추론 프레임워크, 최적화 기법이 끊임없이
  쏟아져 나옵니다. 하드웨어가 낡았거나 구매 절차가 느리면 이 흐름을 따라가기
  어렵습니다. 게다가 호환성이 항상 보장되는 것도 아닙니다. 엔지니어가 인프라에
  쓰는 시간이 늘어날수록 혁신과 출시 속도는 느려집니다.
- **GPU 가용성**: 인프라를 직접 소유하더라도 특히 사용량이 몰리는 시기에는 GPU를
  항상 쓸 수 있는 것은 아닙니다. 확장을 지원하려면 GPU를 추가로 조달해 배포해야
  하며, 여기에는 몇 주에서 몇 달이 걸릴 수 있습니다.
- **인력 요건**: 프로덕션 수준의 추론 스택을 효율적으로 운영하려면 엔지니어에게
  DevOps, InferenceOps, MLOps 전반에 걸친 전문 역량이 필요합니다. 이런 전문
  인력은 채용하기 어렵고, 일반 엔지니어보다 비용이 더 드는 경우가 많습니다.

## 온프레미스 LLM과 클라우드 LLM 비교 {#on-prem-vs-cloud-llms}

온프레미스가 클라우드보다 "더 낫다"는 보편적인 답은 없습니다. 각 선택지는 서로
다른 우선순위에 맞습니다.

- **온프레미스 LLM**은 최대한의 통제권, 더 강력한 데이터 프라이버시, 그리고
  하드웨어를 갖춘 뒤에는 예측 가능한 비용을 제공합니다. 민감한 워크로드나
  꾸준하고 요청량이 많은 트래픽에 이상적입니다.
- **클라우드 LLM**은 자본 투자 없이 유연성, 빠른 구축, 최신 하드웨어에 대한
  접근을 제공합니다. 빠르게 실험해야 하거나, 급증하는 워크로드를 처리해야
  하거나, 인프라 관리를 피하고 싶은 팀에 더 적합합니다.

| 항목                        | 온프레미스 LLM                                                                         | 클라우드 LLM                                                                                                                                            |
|-----------------------------|----------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------|
| **데이터 보안과 규정 준수** | 데이터가 자체 인프라 안에 머무름. 엄격한 규정 준수 요건을 충족하기 쉬움                | 서드파티 공급자가 데이터를 처리함. 규정 준수를 위한 추가 작업이 필요할 수 있음                                                                          |
| **비용 모델**               | 초기 하드웨어 투자가 큼. 꾸준한 트래픽에서는 한계 비용이 낮음                          | 사용한 만큼 지불. 급증하거나 예측하기 어려운 워크로드에 유연하게 대응                                                                                   |
| **성능 통제**               | 지연 시간, 처리량, 확장 동작을 완전히 통제                                             | 공급자의 SLA와 공유 인프라에 따라 제한됨                                                                                                                |
| **확장성**                  | 구매한 하드웨어 범위로 제한됨. LLM을 빠르게 오토스케일링하려면 추가 구성과 설정이 필요 | 온디맨드 GPU 접근으로 사실상 무제한. 다만 LLM의 콜드 스타트를 줄이려면 추가 튜닝이 필요할 수 있음                                                       |
| **유지 보수와 운영**        | 인프라, LLM 전용 관측 가능성, 업데이트를 담당할 전담 팀이 필요                         | 구축은 빠르지만 여전히 어느 정도 인프라 관리가 필요. [BYOC](/getting-started/bring-your-own-cloud/)를 쓰면 부담의 일부를 서비스 공급자에게 넘길 수 있음 |
| **유연성**                  | 장기적이고 안정적인 워크로드에 가장 적합                                               | 빠른 실험과 변화가 많은 워크로드에 가장 적합                                                                                                            |

선택은 보통 규정 준수 요건, 트래픽 패턴, 그리고 팀이 감당할 수 있는 운영
복잡성의 수준에 따라 달라집니다.
