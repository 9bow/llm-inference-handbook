# BYOC(Bring Your Own Cloud)

엔터프라이즈 AI 팀은 한 가지 과제에 직면합니다. 데이터, 인프라, 비용에 대한
통제력을 잃지 않으면서 LLM 워크로드를 빠르게 확장하는 방법입니다.

대부분의 조직은 SaaS 추론 플랫폼으로 시작합니다. 설정이 빠르고 완전 관리형이기
때문입니다. 그러나 워크로드가 커지면 이런 플랫폼은 비싸지고 제약이 많아질 수
있습니다.

- 데이터가 가상 사설 클라우드(VPC) 밖으로 나갑니다
- GPU 시간에 실제로 얼마를 지불하는지 알 길이 없습니다
- 컴플라이언스 심사를 통과하기가 더 어려워집니다

바로 이 지점에서 BYOC(Bring Your Own Cloud)가 등장합니다.

## BYOC(Bring Your Own Cloud)란? {#what-is-bring-your-own-cloud-byoc}

BYOC(Bring Your Own Cloud)는 LLM 추론 플랫폼 같은 벤더의 소프트웨어를 자체
클라우드 계정 안에서 직접 실행할 수 있게 하는 배포 모델입니다. 관리형
오케스트레이션의 편리함을 누리면서도 컴퓨팅, 데이터, 네트워킹을 완전히 직접
통제할 수 있습니다.

이 모델은 최신 AI 인프라에서 특히 중요해졌습니다. 한편으로 AI 모델과 도구는 매우
빠르게 발전합니다. 그래서 추론 스택의 모든 부분을 사내에서 구축하고 유지하면
혁신과 출시 속도가 느려집니다. 다른 한편으로, 특히 민감한 데이터를 다루는
워크로드라면 워크로드를 어디서 어떻게 실행할지는 여전히 직접 정하고 싶기
마련입니다.

BYOC는 이 간극을 메웁니다. 조직은 데이터, 보안, 운영에 대한 통제권을
유지하면서도 벤더가 관리하는 오케스트레이션의 이점을 누릴 수 있습니다. 다시
말해, 컴플라이언스나 주권을 포기하지 않고도 빠르게 움직일 수 있습니다.

간단히 그려 보면 다음과 같습니다.

- **SaaS**: 벤더가 모든 것을 운영합니다.
- **온프레미스**: 사용자가 모든 것을 운영합니다.
- **BYOC**: 벤더가 사용자의 클라우드에서, 사용자의 규칙에 따라 소프트웨어를
  운영합니다.

BYOC는 데이터에 민감한 기업을 위한 틈새 선택지로 시작했습니다. 이제는 대규모 LLM
및 AI 워크로드의 주류 배포 패턴이 되고 있습니다.

## BYOC는 어떻게 동작하나요? {#how-does-byoc-work}

BYOC 배포에서는 사용자와 벤더가 책임을 분담합니다. 벤더는 컨트롤 플레인을
관리하고, 데이터 플레인 구성 요소는 전부 사용자의 클라우드 환경에 남습니다.
고객은 보안과 신뢰성을 보장하기 위해 자체 클라우드 리소스(일부 작업은 벤더에
맡길 수 있음), IAM 권한, 네트워킹 구성을 관리할 책임이 있습니다. 이상적으로는
벤더가 원시 데이터나 사설 네트워크에 직접 접근하는 일이 없어야 합니다.

일반적인 동작 방식은 다음과 같습니다.

1. **컨트롤 플레인(벤더 관리)**: 배포 조정, 스케일링 정책, 스케줄링, 업데이트
   등을 처리합니다. 보안 API를 통해 사용자 환경과 통신합니다.
2. **데이터 플레인(고객 관리)**: 추론이 실제로 일어나는 곳입니다. 모델, GPU,
   컴퓨팅 인스턴스, 데이터가 모두 사용자의 VPC 안에 있으므로 컴플라이언스,
   프라이버시, 완전한 격리를 보장합니다.
3. **네트워킹 및 IAM 경계**: BYOC는 엄격한 권한 범위 설정에 의존합니다. 벤더는
   프로그래밍 방식으로(예: IAM 역할이나 계정 간 접근을 통해) 배포를 관리할 수
   있지만, 데이터를 보거나 유출할 수는 없습니다. 로그(벤더가 디버깅 목적으로
   접근할 수도 있음), 지표, 모델 출력은 사용자 환경 안에 남습니다.

이 하이브리드 설계는 두 방식의 장점을 모두 제공합니다.

- 오케스트레이션과 업데이트를 처리해 주는 관리형 플랫폼의 편리함.
- LLM 워크로드, 데이터, GPU가 직접 통제하에 남아 있다는 확신.

:::note
조직의 요구 사항에 따라 BYOC 구현 방식에는 미묘한 차이가 있을 수 있습니다. 예를
들어 국방이나 의료 같은 산업에서는 팀이 컨트롤 플레인과 데이터 플레인 모두를
완전히 통제해야 할 수도 있습니다. 이렇게 하면 최대한의 보안과 컴플라이언스
보증이 확보되며, 대개 완전히 격리된 환경이나 에어갭(air-gapped) 환경에서
이루어집니다.
:::

vLLM, SGLang, MAX 기반으로 구축된 것과 같은 최신 추론 시스템은 이 모델에
자연스럽게 들어맞습니다. 이런 시스템은 기존 클라우드 인프라에서 실행되면서
중앙의 컨트롤 플레인과 매끄럽게 연결됩니다.

## LLM 워크로드를 위한 BYOC의 이점 {#benefits-of-byoc-for-llm-workloads}

BYOC의 매력은 컴플라이언스를 훨씬 넘어섭니다. 주요 이점은 다음과 같습니다.

### 데이터 주권과 컴플라이언스 {#data-sovereignty-and-compliance}

LLM은 RAG나 AI 에이전트 같은 엔터프라이즈 시스템에 널리 도입되어 있습니다. 이런
애플리케이션은 사설 네트워크 밖으로 나갈 수 없는 민감한 정보(예: 고객 기록)에
접근해야 하는 경우가 많습니다.

BYOC를 사용하면 모든 모델 입력, 출력, 로그가 사용자의 VPC와 클라우드 리전 안에
남습니다. 직접 공유하기로 선택하지 않는 한 어떤 것도 환경 밖으로 나가지
않습니다. 따라서 GDPR 같은 규제 요건을 충족하고 내부 보안 검토를 통과하기가 훨씬
쉬워집니다.

금융, 의료, 공공 부문 조직에게 이 수준의 통제는 필수입니다.

### GPU 유연성과 가용성 {#gpu-flexibility-and-availability}

LLM 추론은 GPU에 크게 의존하며, GPU 공급은 리전과 공급업체에 따라 자주
변동합니다. 많은 벤더가 BYOC에 대해 멀티 클라우드 아키텍처를 지원합니다. AWS,
GCP, Azure 중 어디든, 또는 세 곳을 섞어서든 워크로드를 실행할 위치를 선택할 수
있습니다.

즉, 다음과 같이 할 수 있습니다.

- 워크로드에 가장 좋은 GPU 가용성과 가격을 제공하는 클라우드 공급업체를
  고릅니다.
- 리전별 가격이나 프로모션을 활용합니다.
- 비용과 성능 요구에 맞게 서로 다른 GPU 유형(예: NVIDIA A100, H100, AMD
  MI300X)을 조합합니다.

이런 유연성 덕분에 용량을 기다리느라 발이 묶이거나 컴퓨팅에 과다한 비용을
지불하는 일이 없습니다.

### 비용 최적화와 효율성 {#cost-optimization-and-efficiency}

BYOC를 사용하면 데이터와 같은 환경에서 추론을 실행하므로, 클라우드 간 데이터
전송에서 발생하는 값비싼 송신(egress) 요금을 줄여 줍니다. 대규모 데이터셋을
처리하는 팀이라면 이것만으로도 상당한 비용 절감으로 이어질 수 있습니다.

기존 클라우드 투자를 최대한 활용하는 데도 도움이 됩니다.

- 클라우드 크레딧이나 스타트업 프로그램을 계정 안에서 바로 사용합니다.
- 약정 사용 할인, 절감 플랜, 스팟 가격을 추론 워크로드에 적용합니다.
- 여러 워크로드의 지출을 합산해 공급업체로부터 엔터프라이즈 수준의 할인을
  받습니다.

예를 들어 Modular Cloud BYOC는 사용자의 계정에 직접 컴퓨팅을 프로비저닝합니다.
따라서 이미 보유한 크레딧, 할인, 결제 관계를 그대로 사용해 모델을 배포할 수
있습니다.

### 벤더 종속 없음 {#no-vendor-lock-in}

BYOC는 인프라를 특정 클라우드에 묶이지 않게 유지합니다. 단일 클라우드 공급업체의
스택이나 하드웨어에 얽매이지 않습니다. 따라서 LLM 배포 전략이 미래에도 유효하게
유지됩니다. 요구 사항이 바뀌면 클라우드, GPU, 오케스트레이션 도구 사이에서
워크로드를 자유롭게 옮길 수 있습니다.

## SaaS vs. BYOC vs. 온프레미스 {#saas-vs-byoc-vs-on-prem}

LLM을 어떻게 배포할지 선택하는 일은 본질적으로 모델이 어디에 있고 누가 인프라를
운영하는지의 문제입니다. 각 배포 모델(SaaS, BYOC, 온프레미스)은 통제, 비용,
복잡성 사이에서 서로 다른 트레이드오프를 제공합니다.

간단히 비교하면 다음과 같습니다.

| 모델                                         | 실행 위치                                 | 인프라 관리 주체        | 데이터 통제                                     | 적합한 경우                                                            |
|----------------------------------------------|-------------------------------------------|-------------------------|-------------------------------------------------|------------------------------------------------------------------------|
| SaaS                                         | 벤더의 클라우드                           | 벤더                    | 낮음: 데이터가 벤더의 멀티 테넌트 환경에 있음   | 빠른 설정, 최소한의 운영 부담, 빠른 프로토타이핑, 민감하지 않은 데이터 |
| BYOC                                         | 고객의 클라우드 계정(예: AWS, GCP, Azure) | 벤더와 고객이 공동 관리 | 높음: 데이터가 고객의 VPC에 남음                | 보안/컴플라이언스 요구가 있는 기업, GPU 비용 최적화, 유연한 확장       |
| [온프레미스](/getting-started/on-prem-llms/) | 고객의 사설 데이터 센터                   | 고객                    | 완전: 데이터와 컴퓨팅이 전부 고객 인프라에 남음 | 에어갭 환경 또는 규제가 엄격한 산업(예: 국방, 의료)                    |

대부분의 엔터프라이즈 LLM 워크로드에서 BYOC는 가장 좋은 절충안입니다. 배포가
빠르고, 설계 단계부터 안전하며, 대규모에서도 비용 효율적입니다.

있는 모든 기능을 갖춘 AI 추론 플랫폼을 제공합니다.

## 자주 묻는 질문 {#frequently-asked-questions}

### BYOC를 멀티 클라우드 배포와 함께 사용할 수 있나요? {#can-byoc-work-with-multi-cloud-deployments}

네. BYOC는 멀티 클라우드 아키텍처에 자연스럽게 들어맞습니다. 보안 및
컴플라이언스 정책에 따라 민감한 워크로드는 한 클라우드에 두고, 글로벌 추론
트래픽은 다른 클라우드로 확장할 수 있습니다.

### BYOC는 SaaS와 어떻게 다른가요? {#how-does-byoc-differ-from-saas}

SaaS에서는 벤더가 자체 환경에서 모든 것을 호스팅하고 관리합니다. BYOC에서는
벤더가 컨트롤 플레인을 관리하고 데이터 플레인은 사용자의 클라우드에서
실행됩니다. 컴퓨팅, 스토리지, 네트워크 리소스의 소유권은 사용자에게 남습니다.

### BYOC의 트레이드오프는 무엇인가요? {#what-are-the-trade-offs-of-byoc}

더 많은 주권과 유연성을 얻는 대신 운영 부담의 일부, 즉 자체 클라우드 환경, IAM
역할, 모니터링 관리를 떠안게 됩니다. 많은 팀이 관리형 BYOC 솔루션을 사용해 이
부담을 상쇄합니다.
