# 추론 라우팅

추론 라우팅(inference routing)은 각 LLM 요청을 어느 워커(worker)가 처리할지
결정하는 과정을 말합니다. 규모가 작을 때는 이 결정이 모델 서버나 단순한
게이트웨이 안에 감춰져 있을 수 있습니다. 하지만 배포가 여러 레플리카와 GPU로
커지면 라우팅은 추론 최적화의 중요한 부분이 됩니다.

라우팅 결정은 다음과 같은 사항에 영향을 줍니다:

- 요청이 기존 KV 캐시를 재사용할 수 있는지
- 요청이 오래 실행되는 생성 작업 뒤에서 막히는지
- 대상 워커에 메모리 여유가 충분한지
- 프리필이나 디코드 작업이 이미 워커를 포화시키고 있는지
- 트래픽 패턴이 고르지 않을 때도 전체 GPU 풀이 계속 바쁘게 일하는지

따라서 추론 라우팅은 [프리픽스 캐싱](/inference-optimization/prefix-caching/),
[KV 캐시 오프로딩](/inference-optimization/kv-cache-offloading/),
[프리필-디코드 분리](/inference-optimization/prefill-decode-disaggregation/)
같은 개념과 밀접하게 연결됩니다.

플랫폼 규모에서 라우팅은 경제적인 도구이기도 합니다. 더 나은 배치(placement)는
요청 하나를 더 빠르게 처리하는 데 그치지 않고, 이질적인 테넌트와 급증하는
워크로드 전반에서 GPU가 계속 유용하게 쓰이도록 합니다.

:::note
이 페이지에서 워커는 독립적으로 추론을 실행하고 런타임 상태, 특히 KV 캐시를 일부
소유할 수 있는 라우팅 가능한 단위를 가리킵니다. 배포 방식에 따라 워커는 서로
다른 대상에 대응할 수 있습니다:

- **단일 프로세스 또는 레플리카**. vLLM, SGLang, MAX 또는 이와 유사한 모델 서버
  프로세스입니다.
- **Kubernetes Pod**. 많은 Kubernetes 배포에서는 라우터 관점에서 모델 서빙 Pod
  하나가 워커입니다.
- **노드**. 노드 전체를 하나의 서빙 레플리카로 취급하지 않는 한, 보통 워커와
  같은 것이 아닙니다. 노드 하나에 여러 Pod나 워커가 있을 수 있습니다.
- **GPU 그룹**. 워커는 GPU 하나를 쓸 수도 있고, 텐서 병렬화로 여러 GPU를 쓸 수도
  있으며, 다중 GPU 레플리카 전체를 쓸 수도 있습니다.
:::

## 추론에서 라우팅이 다른 이유 {#why-routing-is-different-for-inference}

전통적인 로드 밸런서는 백엔드를 동일한 블랙박스로 취급합니다. 요청이 들어오면
어느 백엔드든 처리할 수 있고, 응답이 나간 뒤에는 쓸모 있는 상태가 거의 남지
않습니다. 이 방식은 요청이 짧고, 상태가 없고(stateless), 비용이 비슷할 때 잘
동작합니다.

LLM 추론은 이러한 가정을 여러 방식으로 깨뜨립니다:

- **요청은 동등하지 않습니다**. 100 토큰 프롬프트와 100k 토큰 프롬프트는
  메모리와 연산 사용량이 완전히 다릅니다. 어떤 요청은 밀리초 안에 끝나지만, 어떤
  요청은 몇 분 동안 토큰을 생성할 수 있습니다.
- **워커는 상태를 가집니다**. 프리필 단계에서 모델은 이후 요청이 재사용할 수
  있는 KV 캐시를 만듭니다. 하지만 이 재사용은 다음 요청이 올바른 캐시를 이미
  가진 워커에 도달할 때만 일어납니다. 이 점은 프롬프트가 큰 프리픽스를 공유하는
  경우가 많은 멀티턴 채팅과 에이전트 워크플로에서 특히 중요합니다.
- **프리필과 디코드는 서로 다른 자원에 부담을 줍니다**. 프리필은 대부분 연산
  바운드(compute-bound)이고, 디코드는 보통 메모리 대역폭 바운드입니다. 긴 출력을
  디코딩하느라 바쁜 워커도 새 프리필 작업을 받을 수 있고, 그 반대도
  마찬가지입니다. 많은 분산 시스템은 GPU 사이클과 메모리 대역폭의 낭비를
  피하려고 두 단계를 완전히 분리합니다. 자세한 내용은
  [프리필-디코드 분리](/inference-optimization/prefill-decode-disaggregation/)를
  참고하세요.
- **지연 시간 목표는 워크로드마다 다릅니다**. 코드 자동 완성, 채팅 애플리케이션,
  에이전트, 배치 추론 작업은 지연 시간 요구 사항이 모두 다릅니다. 어떤
  워크로드는 낮은 TTFT를 우선하고, 어떤 워크로드는 처리량이나 총비용을 더
  중시합니다. 모든 워커를 똑같이 취급하면 비용이 크고 오래 실행되는 요청이 지연
  시간에 민감한 요청을 방해할 수 있습니다. 예를 들어 사용자는 즉각적인 응답을
  기대하는데도 코드 자동 완성 요청이 긴 에이전트 생성 작업 뒤에서 기다리게 될 수
  있습니다.

라우터가 이런 세부 정보를 보지 못하면 잘못된 결정을 내리기 시작하고, 그 결과는
다음과 같습니다:

- **캐시 재사용 기회 상실**. 후속 요청이 이전 KV 캐시가 없는 워커로 갈 수
  있습니다. 그러면 시스템은 프리픽스 전체를 다시 계산해야 하고, TTFT가
  늘어납니다.
- **지연 시간 증가**. 요청이 디코드 부담이 큰 긴 생성 작업 뒤에서 기다리거나
  캐시 지역성(cache locality)을 잃을 수 있습니다. 캐시 지역성을 잃으면 비용이 큰
  재계산이 필요합니다.
- **처리량 저하**. 새 작업을 처리하는 대신 프리픽스를 재계산하는 데 GPU 시간이
  낭비됩니다.
- **부하 불균형**. 일부 워커는 오래 실행되는 생성 작업으로 과부하가 걸리고, 다른
  워커는 대부분 유휴 상태로 남습니다.

LLM 추론에서는 트래픽을 고르게 나누는 것만으로는 충분하지 않습니다. 그보다
라우터는 서빙 비용을 최소화하고 전체 워커 풀을 효율적이고 반응성 있게 유지해야
합니다.

## 라우팅 전략 {#routing-strategies}

LLM 추론 라우터는 요청을 어디로 보낼지 결정할 때 많은 신호를 사용할 수 있습니다.
정확히 어떤 신호를 쓰는지는 서빙 스택에 따라 다르지만, 가장 유용한 신호는 보통
캐시 지역성, 워커 부하, 메모리 압박, 요청 우선순위에서 나옵니다.

### 라운드 로빈 라우팅 {#round-robin-routing}

라운드 로빈 라우팅(round-robin routing)은 사용 가능한 워커를 순서대로 돌아가며
선택하여 요청을 풀 전체에 고르게 분배합니다. 단순하고 예측 가능하며 기준선으로
쓰기에 유용합니다.

라운드 로빈 라우팅은 요청이 짧고, 프롬프트가 거의 반복되지 않으며, 어느 워커든
대략 같은 비용으로 요청을 처리할 수 있을 때 가장 잘 동작합니다.

단점은 라운드 로빈 라우팅이 캐시를 전혀 고려하지 않는다는 점입니다. 동일한
워커가 `N`개 있고 어피니티(affinity) 메커니즘이 없다면, 후속 요청이 같은 워커에
도달할 확률은 약 `1 / N`에 불과합니다.

긴 프롬프트, 멀티턴 채팅, 에이전트 워크로드에서는 이 때문에 프리필 연산이
반복되고 TTFT가 높아지곤 합니다.

### 무작위 라우팅 {#random-routing}

무작위 라우팅(random routing)은 요청마다 워커를 무작위로 선택합니다.

라운드 로빈처럼 구현하기 쉽고, 라우팅 편향을 거의 만들지 않기 때문에 테스트나
벤치마킹에 유용할 때가 있습니다. 하지만 프리픽스 겹침, 활성 디코드 부하, 큐 깊이
등 추론에 특화된 런타임 정보를 거의 모두 무시합니다.

### 최소 부하 라우팅 {#least-loaded-routing}

최소 부하 라우팅(least-loaded routing)은 새 요청을 활성 요청이나 연결이 가장
적은 워커로 보냅니다.

요청 처리 시간의 편차가 클 때는 이 방식이 라운드 로빈보다 잘 동작합니다. 긴 생성
작업을 여러 개 처리하는 워커는 대부분 유휴 상태인 워커보다 새 트래픽을
자연스럽게 덜 받습니다. 라우터가 신뢰할 만한 캐시 메타데이터를 갖고 있지 않을 때
쓸 만한 대체 방식입니다.

하지만 최소 부하 라우팅도 여전히 캐시를 고려하지 않습니다. 프리필 대부분을
건너뛸 수 있는 적당히 바쁜 워커 대신, 쓸모 있는 프리픽스 캐시가 없는 한가한
워커를 고를 수 있습니다.

### 직접 라우팅 {#direct-routing}

직접 라우팅(direct routing)은 특정 워커를 명시적으로 지정합니다. 예를 들어
게이트웨이, 엔드포인트 피커(endpoint picker), 또는 사용자 정의 스케줄러가 어떤
워커가 대화의 KV 캐시를 갖고 있는지 이미 알고 있을 수 있습니다. 이 경우 서빙
레이어가 라우팅 결정을 다시 내리게 하는 대신, 요청을 해당 워커로 바로
전달합니다.

NVIDIA Dynamo는 대상 워커를 지정하는 라우팅 힌트로 이 방식을 지원합니다.

엄밀히 말해 직접 라우팅은 그 자체로 정책이 아닙니다. 다른 곳에서 내린 결정을
실행하는 방법입니다.

### KV 캐시 사용률 인식 라우팅 {#kv-cache-utilization-aware-routing}

이 전략은 각 워커의 메모리 중 얼마만큼이 이미 KV 캐시로 차 있는지를 고려합니다.

이 점이 중요한 이유는 GPU 연산 사용률 자체는 적당해 보여도 긴 컨텍스트
워크로드가 메모리 압박에 부딪힐 수 있기 때문입니다. KV 캐시 점유율이 높은 워커는
유용한 캐시 블록을 축출(evict)하거나, 새로운 긴 프롬프트를 거부하거나, 배칭
효율을 잃을 수 있습니다. 그런 워커로 요청을 더 보내면 지연 시간과 처리량이
나빠질 수 있습니다.

KV 캐시 사용률 인식 라우터는 새 요청을 메모리 여유가 충분한 워커 쪽으로 보낼 수
있습니다.

</figure>

핵심은 좋은 라우터가 올바른 프리픽스를 가졌다는 이유만으로 워커를 고르지
않는다는 점입니다. 포화된 워커에서의 캐시 적중은 여유가 충분한 워커에서의 더
작은 캐시 적중보다 여전히 느릴 수 있습니다.

오픈소스 커뮤니티는 이미 해결책을 만들고 있습니다.
[Gateway API Inference Extension](https://github.com/kubernetes-sigs/gateway-api-inference-extension)
프로젝트는 엔드포인트 피커(EPP)를 사용하여 각 워커의 KV 캐시 사용률, 큐 길이,
LoRA 어댑터 정보를 수집하고, 요청을 최적의 레플리카로 라우팅합니다.

### 프리픽스 인식 라우팅 {#prefix-aware-routing}

프리픽스 인식 라우팅(prefix-aware routing)은 일치하는 프리픽스를 이미 캐시한
워커로 요청을 보내려고 합니다.

이 방식이 중요한 이유는 프리픽스 캐싱이 캐시된 상태를 재사용할 수 있는 워커에
요청이 도달할 때만 도움이 되기 때문입니다. 단일 모델 서버에서는 캐시가 로컬에
있어서 찾기 쉽습니다. 분산 배포에서는 워커마다 자체 캐시가 있으므로, 라우터는
요청 간에 캐시 지역성을 유지할 방법이 필요합니다.

<figure>
  <Diagram name="prefix-caching-aware-routing" alt="" />
  <figcaption><b>그림 2.</b> 프리픽스를 이미 캐시한 워커로 요청을 라우팅합니다.</figcaption>
</figure>

시스템마다 캐시 지역성을 추정하거나 추적하는 방식이 다릅니다:

- **프리픽스 어피니티**. 어피니티 메커니즘을 사용하여 비슷한 프리픽스를 가진
  요청을 같은 워커로 라우팅합니다. 단순한 구현은 같은 클라이언트 IP에서 온
  요청을 같은 백엔드로 보내는 것처럼 클라이언트 수준의 세션 어피니티에 의존할 수
  있습니다. 구현하기 쉽지만, 특정 클라이언트나 프리픽스에 요청이 몰리면 워커에
  과부하가 걸릴 수 있습니다. 또한 서로 다른 클라이언트 간의 캐시 재사용 기회를
  놓칩니다.
- **프리픽스 인식 일관된 해싱(consistent hashing)**. 라우터가 요청 프리픽스의
  일부를 해싱하여 비슷한 프롬프트가 같은 워커나 가까운 워커에 도달하게 합니다.
  예를 들어 단순한 전략은 프롬프트의 처음 N개 토큰이나 문자만 해싱할 수
  있습니다. 이 방식은 라우팅 메타데이터가 거의 필요 없지만, 효과는 해싱 전략의
  품질과 프롬프트 길이 분포에 크게 좌우됩니다.
- **라우터의 근사 프리픽스 캐시**. 라우터가 모든 백엔드 서버의 프리픽스 캐시에
  대한 근사 조회 캐시를 유지하게 합니다. 이렇게 하면 세부적인 캐시 보고가 필요
  없지만, 축출이나 재시작 이후 라우터가 보는 정보가 오래될 수 있습니다.
- **정밀한 캐시 인식 라우팅**. 워커가 KV 캐시 이벤트나 세부 캐시 메타데이터를
  내보내서, 라우터가 캐시 배치 상황에 대한 정확한 전역 뷰를 유지할 수 있게
  합니다. 예를 들어
  [llm-d](https://llm-d.ai/docs/guides/precise-prefix-cache-aware)는 vLLM과
  SGLang의 KV 캐시 이벤트를 사용하여 캐시 블록이 서빙 Pod 중 어디에 있는지
  추적합니다. 그런 다음 스케줄러는 들어온 요청의 프리픽스 중 얼마만큼을 각
  워커에서 이미 사용할 수 있는지를 기준으로 워커에 점수를 매깁니다. 또한 캐시
  지역성을 부하 인식 신호와 결합하여 요청이 몰리는 레플리카에 과부하가 걸리지
  않게 합니다.

일반적으로 캐시 신호가 정확할수록 캐시 재사용이 늘고 반복되는 프리필 작업이
줄어듭니다. 그 대가로 조정 비용이 커지고, 메타데이터 교환이 늘며, 라우팅
레이어의 작업이 많아집니다.

### 프리필/디코드 인식 라우팅 {#prefilldecode-aware-routing}

프리필과 디코드를 서로 다른 워커로 나누면 라우팅은 더 흥미로워집니다. 분리된
구성에서 라우터는 다음을 결정해야 할 수 있습니다:

- 요청이 로컬 프리필을 쓸지, 별도의 프리필 워커를 쓸지
- 어느 디코드 워커가 진행 중인 생성 작업을 맡을지
- 프리필 워커와 디코드 워커 사이에서 KV 캐시를 어떻게 옮길지
- 캐시 지역성이 전송 비용을 감수할 만한 가치가 있는지

짧은 프롬프트에서는 워커 간에 KV 캐시를 옮기지 않아도 되므로 로컬 프리필이 더
빠를 수 있습니다. 캐시 겹침이 큰 긴 프롬프트에서는 기존 캐시를 재사용할 수 있는
워커로 라우팅하는 것이 더 중요할 수 있습니다. 라우팅 정책은 연산 비용과 데이터
이동을 모두 고려해야 합니다.

이 때문에 추론 라우팅은 단순히 네트워크 레이어의 문제가 아닙니다. 모델 런타임,
스케줄러, 캐시 관리자의 정보가 필요합니다.

## 하이브리드 점수 산정 {#hybrid-scoring}

일부 추론 라우터는 다중 신호 점수 산정 시스템으로 발전합니다. 여러 요소를
결합하여 각 워커의 서빙 비용을 추정합니다.

- **프리픽스 및 KV 캐시 적중 확률**. 워커에 요청 프리픽스 일부에 대한 KV 캐시가
  이미 있는가?
- **KV 캐시 메모리 사용률**. 활성 KV 상태나 캐시된 KV 상태가 GPU 메모리를 얼마나
  차지하고 있는가? 워커가 축출 압박에 가까운가?
- **큐 길이**. 대기 중인 요청이 몇 개인가?
- **활성 토큰과 디코드 부하**. 현재 생성 중인 토큰이 몇 개인가? 이 값은 디코드
  단계의 메모리 대역폭 압박을 가늠하는 좋은 대리 지표인 경우가 많습니다.
- **LoRA 어댑터 가용성**. 워커에 올바른 어댑터가 이미 로드되어 있는가? 처리 도중
  어댑터를 교체하는 것은 비용이 큽니다.
- **프리필 대 디코드 역할**. 분리된 구성에서 이 워커는 프리필 전용인가, 디코드
  전용인가?
- **SLA 또는 우선순위 등급**. 요청에 엄격한 지연 시간 요구 사항이나 더 높은
  스케줄링 우선순위가 있는가?

여러 오픈소스 프로젝트가 이미 이 방향을 따르고 있습니다:

- [SGLang 라우터](https://github.com/sgl-project/sglang/blob/4d2a88bdffe91168dfc73ef7e3bc9100ba96686b/sgl-router/src/router.rs#L61)는
  부하 분산을 대체 수단으로 두는 캐시 인식 라우팅 휴리스틱을 사용합니다. 기수
  트리(radix tree)와 큐 카운트로 근사적인 프리픽스 지역성을 추적하고, 시스템
  불균형 정도에 따라 캐시 인식 라우팅과 최단 큐 라우팅 사이를 전환합니다.
- [Dynamo](https://docs.nvidia.com/dynamo/components/router/router-guide)는 워커
  전반의 프리필 비용과 디코드 비용을 모두 추정하여 요청을 라우팅합니다. KV 캐시
  겹침, 활성 디코드 블록, 워크로드 배치를 고려하여 중복 연산을 줄이고 서빙
  효율을 높입니다.
- [llm-d](https://llm-d.ai/docs/architecture/core/router)는
  [Gateway API Inference Extension](https://github.com/kubernetes-sigs/gateway-api-inference-extension)
  프로젝트 위에 추론 스케줄링을 구축합니다. 캐시 지역성, 워커 부하, 기타 런타임
  신호를 결합하여 Kubernetes에서 지능적인 요청 라우팅과 스케줄링을 제공합니다.

## 자주 묻는 질문 {#faqs}

### 추론 라우팅은 부하 분산과 같은가요? {#is-inference-routing-the-same-as-load-balancing}

추론 라우팅은 부하 분산을 포함하지만 범위가 더 넓습니다. 일반적인 로드 밸런서는
주로 트래픽을 여러 백엔드에 나눕니다. 추론 라우터는 여기에 더해 캐시 지역성, KV
캐시 메모리 압박, 어댑터 상태, 프리필 비용, 디코드 부하, 요청 우선순위와 SLA도
고려합니다.

### 캐시 인식 라우팅은 항상 지연 시간을 줄이나요? {#does-cache-aware-routing-always-reduce-latency}

경우에 따라 다릅니다. 과부하 걸린 워커에서의 캐시 적중은 한가한 워커에서의 더
작은 캐시 적중보다 느릴 수 있습니다. 좋은 라우터는 캐시 적중만 최적화하지 않고,
캐시 겹침을 큐 신호와 용량 신호와 함께 고려합니다.

### 모든 셀프 호스팅 LLM 배포에 캐시 인식 라우팅을 써야 하나요? {#should-every-self-hosted-llm-deployment-use-cache-aware-routing}

꼭 그렇지는 않습니다. 트래픽이 적거나, 프롬프트가 짧거나, 캐시 재사용이 드물다면
단순한 라우팅으로 시작하세요. 반복되는 컨텍스트와 분산된 워커 때문에 재계산
비용이 커질 때 캐시 인식 라우팅을 추가하세요.
