# LLM 추론의 핵심 지표(key metrics)

최적화 기법을 살펴보기 전에, 그 기법들이 겨냥하는 핵심 지표부터 이해해야 합니다.
LLM 성능 평가에는 다양한 도구가 쓰이는데, 도구마다 이 지표들을 정의하고 측정하고
계산하는 방식이 다릅니다.

## 지연 시간 {#latency}

지연 시간(latency)은 모델이 요청에 얼마나 빨리 응답하는지를 나타냅니다. 지연
시간은 사용자 경험에 매우 중요하며, 특히 대화형 실시간 애플리케이션에서 더욱
그렇습니다.

<LatencyMetrics />

지연 시간을 측정하는 핵심 지표는 다음과 같습니다.

- **TTFT(Time to First Token)**: 요청을 보낸 뒤 첫 번째 토큰이 생성될 때까지
  걸리는 시간입니다. 모델이 얼마나 빨리 응답을 시작하는지를 보여 줍니다.
- **E2EL(End-to-End Latency)**: 요청을 보낸 시점부터 사용자 쪽에서 마지막 토큰을
  받을 때까지의 시간입니다. E2EL은 사용자가 체감하는 응답성에 직접 영향을
  줍니다. TTFT가 빨라도 이후 토큰 생성이 느리면 사용자 경험은 여전히 나쁩니다.
- **토큰 생성 시간**: 첫 번째 토큰 이후 나머지 토큰을 모두 스트리밍하는 데
  걸리는 시간입니다. 안정적인 생성 구간만 측정하므로 TTFT는 제외합니다.

  $$
  \text{Token Generation Time} = {\text{E2EL – TTFT}}
  $$

- **TPOT(Time per Output Token)**: 첫 토큰 이후 각 토큰이 생성되는 평균 시간
  간격입니다(TTFT 제외). TPOT가 낮을수록 모델이 토큰을 더 빨리 만들어 내므로
  초당 토큰 수가 늘어납니다. TPOT는 보통 다음과 같이 계산합니다.

  $$
  \text{TPOT} = \frac{\text{E2EL – TTFT}}{\text{Total Output Tokens} - 1}
  $$

  ChatGPT 인터페이스처럼 사용자 눈앞에 텍스트가 한 단어씩 나타나는 스트리밍
  상황에서는 TPOT가 경험이 얼마나 매끄럽게 느껴지는지를 결정합니다. 매끄러운
  경험을 보장하려면 시스템이 사람의 읽기 속도를 따라가거나 넘어서는 것이
  이상적입니다.

- **ITL(Inter-Token Latency)**: 연속된 두 토큰 사이의 정확한 대기 시간입니다.

  단일 요청에서는 모든 ITL의 평균이 TPOT와 같습니다. 그래서
  **두 지표를 같은 의미로 쓰는 경우도 있습니다**.

  $$
  \text{Average ITL} = \text{TPOT}
  = \frac{\text{E2EL – TTFT}}{\text{Total Output Tokens} - 1}
  $$

  그러나 여러 요청에 걸쳐 계산하면 평균을 내는 방식에서 차이가 생깁니다.

  $$
  \text{Average ITL}
  = \frac{\text{Sum of all ITLs across Requests}}
         {\text{Total Output Tokens across Requests}}
  $$

  이 경우 평균 ITL은 평균 TPOT와 다릅니다. 평균 TPOT는 보통 다음과 같이 계산하기
  때문입니다.

  $$
  \text{Average TPOT}
  = \frac{\text{TPOT}_1 + \text{TPOT}_2 + \cdots + \text{TPOT}_N}{N}
  $$

  벤치마크 결과를 읽을 때는 TPOT와 ITL이 어떻게 정의되었는지 항상 확인하세요.
  프레임워크와 논문마다 이 지표를 계산하고 사용하는 방식이 다를 수 있으며, 그에
  따라 성능 수치를 해석하는 방식도 달라져야 합니다. 위의 여러 요청에 대한
  수식에서는 다음과 같습니다.

  - **평균 TPOT는 요청 단위로 가중됩니다**. 시스템이나 구성 간에 요청별 지연
    시간을 비교할 때 유용합니다. 생성된 토큰 수와 관계없이 모든 요청을 동일하게
    취급합니다.
  - **평균 ITL은 토큰 단위로 가중됩니다**. 따라서 더 긴 응답(전체 토큰 수에 더
    많이 기여하는 응답)이 더 큰 가중치를 가집니다. 전체 시스템 처리량과 정상
    상태 성능(예: 집계 스트리밍 속도)을 측정하는 데 더 적합합니다.

허용 가능한 지연 시간은 사용 사례에 따라 다릅니다. 예를 들어 챗봇은 반응이
빠르다고 느껴지려면 TTFT가 500밀리초 미만이어야 할 수 있습니다. 반면 코드 자동
완성 도구는 개발자 경험이 끊기지 않도록 TTFT가 100밀리초 미만이어야 할 수도
있습니다. 이와 달리 하루에 한 번 검토하는 긴 보고서를 생성한다면 총 지연 시간이
30초여도 전혀 문제가 없을 수 있습니다. 핵심은 지연 시간 목표를 해당 작업의
속도와 기대치에 맞추는 것입니다.

### 평균, 중앙값, P99 지연 시간의 이해 {#understanding-mean-median-and-p99-latency}

LLM 성능, 특히 지연 시간을 분석할 때는 숫자 하나만 보아서는 충분하지 않습니다.
평균, 중앙값, P99 같은 지표는 각각 전체 상황의 서로 다른 측면을 보여 줍니다.

- **평균(Mean)**: 모든 값의 합을 값의 개수로 나눈 것입니다. 평균은 전반적인
  성능을 대략 파악하게 해 주지만, 극단값(이상치) 때문에 왜곡될 수 있습니다. 예를
  들어 요청 하나의 TTFT가 유난히 느리면 평균이 부풀려집니다.
- **중앙값(Median)**: 모든 값을 정렬했을 때 가운데에 있는 값입니다. 중앙값은
  일반적인 사용자 경험을 보여 줍니다. 평균보다 안정적이고 이상치의 영향을 덜
  받습니다. 중앙값 TTFT가 30초라면 대부분의 사용자가 첫 응답을 매우 느리게 받고
  있다는 뜻이며, 실시간 사용 사례에서는 받아들이기 어려울 수 있습니다.
- **P99(99번째 백분위수)**: 전체 요청의 99%가 그 아래에 속하는 값입니다. P99는
  가장 느린 1% 요청의 최악의 경우 성능을 드러냅니다. 사용자가 일관성을
  기대하거나, SLA에서 99%의 경우에 빠른 응답을 보장할 때 중요합니다. P99 TTFT가
  100초에 가깝다면 적지만 무시할 수 없는 비율의 사용자가 매우 오래 기다리고
  있다는 뜻입니다.
  :::note
  P90이나 P95도 볼 수 있는데, 각각 90번째와 95번째 백분위수 지연 시간을
  나타냅니다. 이 값들은 최악에 가까운 경우의 성능을 이해하는 데 유용하며, P99가
  너무 엄격하거나 노이즈에 민감할 수 있는 경우에 자주 쓰입니다.
  :::

이 지표들을 함께 보면 전체 그림을 파악할 수 있습니다.

- **평균**은 시간에 따른 추세를 모니터링하는 데 도움이 됩니다.
- **중앙값**은 대다수 사용자의 경험을 반영합니다.
- **P99**는 꼬리 지연 시간(tail latency)을 포착합니다. 꼬리 지연 시간은
  프로덕션에서 사용자 경험을 좌우할 수 있습니다.

LLM 성능 벤치마크에서는 지연 시간과 사용자 경험의 여러 측면을 포착하기 위해 평균
TTFT, 중앙값 TPOT, P99 E2EL 같은 지표를 자주 볼 수 있습니다.

## 처리량 {#throughput}

처리량(throughput)은 LLM이 주어진 시간 동안 얼마나 많은 작업을 처리할 수
있는지를 나타냅니다. 많은 사용자에게 동시에 서비스하거나 대량의 데이터를 처리할
때는 높은 처리량이 필수입니다.

처리량을 측정하는 일반적인 방법은 두 가지입니다.

- **RPS(Requests per Second)**: LLM이 1초 동안 성공적으로 완료할 수 있는 요청
  수를 나타내는 지표입니다. 다음과 같이 계산합니다.

    ```bash
    Requests per second = Total completed requests / (T1 - T2)
    ```

  :::note
  여기서 T1과 T2는 초 단위의 시간 구간을 나타냅니다.
  :::
  RPS는 LLM이 동시 요청을 얼마나 잘 처리하는지 대략 보여 주지만, 각 요청에
  필요한 작업량은 반영하지 않습니다. 예를 들어 `“Hi there!”` 같은 짧은 인사말을
  생성하는 일은 긴 에세이를 쓰는 일보다 훨씬 부담이 적습니다. 따라서 입력 및
  출력 길이나 트래픽 패턴이 다른 워크로드 간에 RPS를 직접 비교하면 잘못된 결론에
  이를 수 있습니다.

  RPS에 영향을 주는 요인은 다음과 같습니다.

  - 프롬프트의 복잡도와 길이
  - 모델 크기와 하드웨어 사양
  - 최적화(예: 배칭, 캐싱, 추론 엔진)
  - 요청당 지연 시간

- **TPS(Tokens per Second)**: 활성 상태인 모든 요청에서 매초 처리되는 토큰 수를
  측정해 처리량을 더 세밀하게 보여 주는 지표입니다. 두 가지 형태가 있습니다.

  - **입력 TPS**: 모델이 초당 처리하는 입력 토큰 수입니다.
  - **출력 TPS**: 모델이 초당 생성하는 출력 토큰 수입니다.

  두 지표를 모두 이해하면 추론 워크로드의 특성에 따라 성능 병목을 찾아낼 수
  있습니다. 예를 들면 다음과 같습니다.

  - 긴 문서(예: 2,000토큰 입력)를 포함하는 요약 요청에서는 입력 TPS가 더
    중요합니다.
  - 짧은 [프롬프트](/model-interaction/prompt-engineering/)로 긴 답변을 생성하는
    챗봇(예: 20토큰 프롬프트 → 500토큰 응답)은 출력 TPS에 크게 좌우됩니다.

  벤치마크를 검토하거나 LLM 성능을 평가할 때는
  **TPS 지표가 입력, 출력, 합산 중 무엇을 가리키는지 항상 확인하세요**. 사용
  사례에 따라 각 지표가 드러내는 강점과 한계가 다릅니다.

  TPS에 영향을 주는 요인은 다음과 같습니다.

  - 배치 크기(배치가 클수록 포화 지점까지는 TPS가 높아질 수 있음)
  - KV 캐시 효율과 메모리 사용량
  - 프롬프트 길이와 생성 길이
  - GPU 메모리 대역폭과 연산 사용률

  이런 요인 때문에 TPS는 부풀리기 쉬워서 잘못 해석하기도 쉽습니다. 예를 들면
  다음과 같습니다.

  - 프롬프트가 짧으면 TTFT가 낮아지고 요청마다 필요한 작업량이 줄어듭니다.
    요청당 작업량이 적으면 TPS가 실제보다 높아 보입니다.
  - 배치를 키우고 동시성을 높이면 GPU를 계속 바쁘게 유지해 전체 TPS를 높일 수
    있지만, 대기열 시간, TTFT, 사용자별 TPOT가 늘어날 수 있습니다.

    동시 요청 수가 늘어나면 전체 TPS도 함께 늘어나다가, LLM이 사용 가능한 연산
    자원의 포화 지점에 도달합니다. 이 지점을 넘으면 LLM이 수용 한계를 초과하므로
    성능이 떨어질 수 있습니다.

## 굿풋 {#goodput}

굿풋(goodput)은 처리량 개념을 더 정교하게 다듬은 지표입니다. 굿풋은 LLM이 사전에
정의한 서비스 수준 목표(SLO)를 충족하면서 초당 몇 개의 요청을 성공적으로
완료하는지를 측정합니다. 서비스 품질을 직접 반영하므로 실제 배포 환경에서 훨씬
유용한 지표입니다.

:::info

**서비스 수준 목표**(Service-Level Objective, SLO)는 특정 지표의 목표 성능
수준을 정의합니다. 어떤 수준의 서비스를 허용 가능하다고 볼지 기준을 정합니다.
예를 들어 TTFT에 대한 SLO는 챗봇 상호작용의 95%에서 TTFT가 200밀리초 미만이어야
한다고 명시할 수 있습니다. SLO는 보통 서비스 공급자와 사용자 사이의 더 포괄적인
서비스 수준 계약(SLA)의 핵심 요소입니다.

:::

굿풋은 왜 중요할까요? 처리량이 높다고 해서 항상 사용자 경험이 좋은 것은
아닙니다. 지연 시간 목표를 충족하지 못하면 그 요청 중 상당수는 쓸모가 없을 수
있습니다. 굿풋은 LLM 서빙 시스템이 지연 시간 제약 아래에서 성능 목표와 사용자
경험 목표를 얼마나 잘 충족하는지를 직접 보여 주는 척도입니다. 굿풋을 보면 실제
사용자 경험과 비용 효율을 희생하면서 처리량만 극대화하는 함정을 피할 수
있습니다.

## 지연 시간과 처리량의 트레이드오프 {#latency-vs-throughput-tradeoffs}

LLM 추론을 호스팅하고 최적화할 때는 지연 시간 최소화와 처리량 극대화라는 두 가지
핵심 목표 사이에서 항상 균형을 잡아야 합니다. 그 의미를 하나씩 살펴보겠습니다.

| 목표                           | 의미                                                                                                                                                                                       |
|--------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 처리량 극대화(TPS/MW)          | 와트당 최대한 많은 토큰을 서빙하는 데 집중합니다. 보통 더 큰 배치 크기와 공유 연산 자원을 사용합니다. 하지만 개별 사용자의 응답은 느려질 수 있습니다.                                      |
| 지연 시간 최소화(사용자당 TPS) | 각 사용자에게 빠른 응답(낮은 TTFT)을 제공하는 데 집중합니다. 보통 작은 배치와 격리된 연산 자원을 사용하지만, 그만큼 GPU를 덜 효율적으로 쓰게 됩니다.                                       |
| 둘 사이의 균형                 | 일부 시스템은 동적인 균형을 목표로 합니다. 워크로드, 사용자 우선순위, 앱 요구 사항에 따라 자원 사용을 실시간으로 조정합니다. SLO가 서로 다른 다양한 애플리케이션을 서빙할 때 이상적입니다. |

적절한 균형은 워크로드에 따라 다릅니다. 애플리케이션마다 지연 시간을 체감하는
방식이 다르므로, 우선시할 지표는 사용자나 다운스트림 시스템이 응답을 소비하는
방식을 반영해야 합니다. 다음은 몇 가지 제안입니다.

| 사용 사례                           | 주요 지표                  | 중요한 이유                                                                         |
|-------------------------------------|----------------------------|-------------------------------------------------------------------------------------|
| 대화형 채팅                         | TTFT, 그다음 ITL 또는 TPOT | 사용자는 응답이 언제 시작되는지, 그리고 매끄럽게 스트리밍되는지를 중요하게 여깁니다 |
| 긴 형식 스트리밍                    | ITL 또는 TPOT, 그리고 E2EL | 첫 토큰 이후에는 생성 속도가 경험을 좌우합니다                                      |
| 에이전트형 또는 다단계 워크플로     | E2EL                       | 다운스트림 단계는 보통 전체 응답이 나올 때까지 진행할 수 없습니다                   |
| 대량 오프라인 처리                  | TPS와 토큰당 비용          | 개별 요청의 지연 시간보다 전체 효율이 더 중요합니다                                 |
| 지연 시간 제약이 있는 온라인 서비스 | 굿풋                       | 지연 시간 SLO를 충족한 완료 요청만 계산에 포함됩니다                                |

어떤 지표가 가장 중요한지 파악했다면 시스템을 적절한 균형점으로 조정할 수
있습니다. 중요한 시스템 수준의 조정 항목으로는 데이터 병렬화(DP), 텐서
병렬화(TP), 전문가 병렬화(EP), 배치 크기, 정밀도(예: FP8, FP4), 분리(프리필과
디코드를 나누는 것)가 있습니다. 각각은 성능의 한 측면을 개선할 수 있지만 다른
곳에서 비용을 늘릴 수 있습니다. 가장 좋은 구성은 단순히 가장 높은 처리량이나
가장 낮은 지연 시간을 내는 구성이 아니라, 워크로드의 SLO를 충족하는 구성입니다.

서버리스 API를 사용하면 이런 최적화가 추상화되어 감춰질 수 있으며, 그만큼 세부
조정에 대한 통제권이 줄어듭니다. 반면 프로그래밍 가능한 저수준 스택을 직접
구축하면 이런 트레이드오프를 직접 다루면서 시스템 성능을 앱의 특정 SLO에 맞출 수
있습니다.
