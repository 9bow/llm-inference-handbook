# LLM 추론을 위한 커널 최적화(kernel optimization)

LLM 추론 속도를 높이는 이야기를 할 때 사람들은 보통 배칭, 캐싱, 라우팅부터
떠올립니다. 그럴 만합니다. 이런 기법은 눈에 잘 띄는 시스템 수준의 수단이기
때문입니다.

하지만 그 모든 것의 아래에는 실제 작업을 조용히 처리하는 레이어가 있습니다. 바로
GPU 커널입니다.

## 커널 최적화란? {#what-is-kernel-optimization}

LLM이 토큰을 생성할 때 GPU는 행렬 곱, 어텐션, 정규화, 활성화 함수처럼 병렬성이
매우 높은 연산을 차례로 실행합니다. 이 연산들은 GPU 커널로 구현됩니다. GPU
커널은 수많은 GPU 스레드에서 동시에 실행되는 함수입니다.

어떤 연산은 커널 하나에 대응하고, 어떤 연산은 여러 커널로 구성됩니다. 여러
연산을 커널 하나로 융합할 수 있는 경우도 많은데, 이는 가장 효과가 큰 최적화 중
하나입니다.

커널은 LLM 추론의 내부 루프라고 생각하면 됩니다. 커널은 토큰 생성 단계마다 핵심
수치 연산을 처리하며, 실제 연산 시간 대부분이 커널에서 소비됩니다.

커널 최적화는 다음과 같은 방법으로 이 함수들을 더 빠르고 효율적으로 실행되게
만드는 작업입니다:

- 연산당 지연 시간 줄이기
- 하드웨어 사용률 높이기(연산 유닛, 메모리 대역폭 등)
- 메모리 이동과 데이터 전송 최소화하기

크게 보면 GPU를 얼마나 세밀하게 제어하고 싶은지에 따라 커널 최적화에는 두 가지
일반적인 접근 방식이 있습니다.

- **직접 작성한 커널**. 전통적인 방식입니다. 보통 CUDA나 Triton 같은 고수준 커널
  DSL을 사용하여 GPU 커널을 직접 작성하고 튜닝합니다. 예를 들면 다음과 같습니다:
  - 사용자 정의 CUDA 커널
  - FlashAttention 같은 최적화된 어텐션 구현

  이 방식은 세밀한 제어가 가능합니다. 메모리 접근, 스레드 배치, 연산 스케줄을
  처음부터 설계하고 튜닝할 수 있습니다. 하지만 GPU 아키텍처에 대한 깊은 지식이
  필요하므로 어렵기도 합니다.

  :::note
  Triton에서도 커널을 작성하는 것은 마찬가지지만, 타일 기반 프로그래밍 모델이
  저수준 세부 사항을 많이 감춰 줍니다. 워프를 수동으로 관리할 필요가 없고,
  일반적인 패턴에서는 공유 메모리 스케줄링을 명시적으로 할 필요도 없습니다. 그래서
  Triton은 CUDA 커널을 그대로 작성하는 것보다 쉽습니다. 또한 완전히 컴파일러에
  맡기는 방식보다 더 많은 제어권을 제공합니다.
  :::

- **컴파일러 기반 최적화**. TVM이나 XLA 같은 컴파일러 시스템에 의존하여,
  고수준의 연산 기술(description)로부터 최적화된 커널을 생성합니다. 이런
  시스템은 다음을 할 수 있습니다:
  - 여러 연산을 커널 하나로 융합하기
  - 효율을 높이도록 연산 순서 재배치하기
  - 최적화된 커널을 자동으로 생성하기

  이 모델에서는 무엇을 계산할지만 기술하면, 컴파일러가 타깃 하드웨어 백엔드에서
  이를 효율적으로 실행할 방법을 결정합니다. 덕분에 진입 장벽이 크게 낮아집니다.
  하지만 저수준 실행을 직접 제어하기 어렵고, 새로운 모델 아키텍처나 특수한 연산
  패턴을 지원하는 데에서는 직접 작성한 커널보다 뒤처질 수 있습니다.

## 커널 최적화가 아닌 것 {#what-kernel-optimization-is-not}

커널 최적화는 [추론 최적화](/inference-optimization/) 장에서 다루는 다른 최적화
기법과 혼동하기 쉽습니다. 다음은 커널 최적화가 아닙니다:

- 연속 배칭 또는 동적 배칭
- 프리픽스 캐싱
- KV 캐시 라우팅 또는 오프로딩
- GPU 간 부하 분산
- 멀티 리전 또는 멀티 클라우드 배포

이런 기법은 커널 위의 시스템 레이어와 런타임 레이어에서 동작합니다. 커널
최적화는 한 단계 더 깊이 들어가, 실제로 연산을 수행하는 GPU 코드를 다룹니다.

둘을 간단히 구분하면 다음과 같습니다:

- 커널 최적화: 단일 연산이 GPU에서 얼마나 빠르게 실행되는가
- 시스템 최적화: 요청이 전체 서빙 인프라를 얼마나 효율적으로 흘러가는가

둘 다 중요합니다. 다만 근본적으로 서로 다른 문제를 해결할 뿐입니다.

## 대부분의 팀이 이 레이어를 건드리지 않는 이유 {#why-most-teams-never-touch-this-layer}

대부분의 AI 엔지니어는 GPU 커널을 한 번도 작성하지 않으며, 거기에는 그럴 만한
이유가 있습니다. vLLM, SGLang, TensorRT LLM 같은 추론 프레임워크가 저수준 실행을
모두 추상화하기 때문입니다.

따라서 다음만 하면 됩니다:

- 모델 로드하기
- API 호출하기
- 제품 기능에 집중하기

이러한 추상화는 의도된 것입니다. 현대 추론 프레임워크의 목표 중 하나는 GPU의
복잡성을 보이지 않게 만드는 것입니다. 게다가 프레임워크가 이미 만족할 만한
성능을 낸다면 더 깊이 들어갈 뚜렷한 이유가 없습니다.

## 그래도 커널 최적화가 중요한 이유 {#why-kernel-optimization-still-matters}

커널을 직접 작성하지 않더라도, 커널 레이어는 그 위에 있는 모든 것의 상한을
정합니다.

### 새로운 아키텍처에는 새로운 커널이 필요합니다 {#new-architectures-need-new-kernels}

새로운 모델 아키텍처가 나오면 새로운 패턴이 함께 등장하는 경우가 많습니다:

- 새로운 어텐션 메커니즘
- 새로운 텐서 형태
- 새로운 연산 순서

이를 지원하려면 PyTorch로 작성하는 것만으로는 부족합니다. 새로운 커널이나 연산을
융합하는 새로운 방법이 필요할 때가 많습니다.

vLLM이나 SGLang 같은 프레임워크는 미리 빌드되고 미리 최적화된 커널 라이브러리에
의존합니다. 이런 프레임워크가 모든 새로운 아이디어를 첫날부터 자동으로
지원하지는 않습니다. 누군가 새로운 연산 패턴에 맞는 효율적인 커널을 작성하고
통합하기 전까지, 프레임워크는 더 느린 범용 구현으로 대체하거나 그 아키텍처를
아예 지원하지 못합니다.

그래서 다음 두 시점 사이에는 종종 간극이 생깁니다:

- 모델이 공개되는 시점
- 그 모델이 프로덕션에서 효율적으로 실행되는 시점

FlashAttention이 좋은 예입니다. FlashAttention은 어떤 추론 프레임워크가 발명한
기능이 아니었습니다. 독립적인 커널 최적화였고, 그 가치가 입증된 뒤에
프레임워크들이 채택했습니다.

### 성능 상한은 실재합니다 {#the-performance-ceiling-is-real}

고수준 프레임워크는 어떤 의미에서 커널 모음 위에 구축된 오케스트레이션
레이어입니다. vLLM, SGLang, TensorRT LLM은 모두 결국 실제 연산을 위해 커널을
디스패치합니다. 즉 추론 속도는 하위 커널이 허용하는 수준을 넘을 수 없습니다.

시스템 수준 최적화가 도움이 될 수는 있지만, 비효율적인 커널을 완전히 보완하지는
못합니다. 병목이 커널 자체에 있다면 런타임 수준에서 무엇을 바꾸더라도 그 격차를
메울 수 없습니다.

### 하드웨어 이식성 {#hardware-portability}

사용자 정의 CUDA 커널을 작성하면 그 커널은 NVIDIA GPU에서만 실행됩니다. 이는
종속(lock-in)을 만듭니다:

- AMD GPU나 다른 가속기로 옮기기가 어려워집니다
- 커널을 처음부터 다시 작성해야 할 수도 있습니다

그래서 이식성 레이어와 컴파일러 기반 솔루션이 점점 더 중요해지고 있습니다. 이런
솔루션은 다음 두 가지 사이의 어려운 트레이드오프를 해결하려고 합니다:

- **특정 백엔드에서의 최고 성능**
- **여러 하드웨어 백엔드에 걸친 폭넓은 이식성**

대부분의 팀은 둘 다 원합니다. 하지만 현재 이를 온전히 제공하는 솔루션은 거의
없습니다. 한 GPU 아키텍처에 맞춰 세심하게 튜닝한 커널은 상당한 재작업 없이는
다른 아키텍처에서 좋은 성능을 내지 못하는 경우가 많습니다.

## 자주 묻는 질문 {#faqs}

### GPU 커널이란? {#what-is-a-gpu-kernel}

GPU 커널은 수많은 GPU 스레드에서 병렬로 실행되는 작은 프로그램입니다.

LLM 추론에서 커널은 다음과 같은 실제 수학 연산을 처리합니다:

- 행렬 곱
- 어텐션 연산
- 정규화와 활성화 함수

커널은 GPU에서 실행되는 작업 단위라고 생각하면 됩니다. 모델이 토큰을 생성할 때
내부적으로 많은 커널이 실행됩니다.

### 커널 융합이란? {#what-is-kernel-fusion}

커널 융합(kernel fusion)은 여러 연산을 GPU 커널 하나로 합치는 것을 말합니다.
핵심 이점은 메모리 이동과 커널 실행 오버헤드를 줄이는 것입니다.

샌드위치를 만든다고 생각해 봅시다. 융합하지 않으면 연쇄된 각 연산이 별개의
작업이 됩니다:

1. **작업 1**: 냉장고에 가서 빵을 꺼내 조리대로 가져온 다음, 굽고 나서 다시 넣어
   둡니다
2. **작업 2**: 냉장고에 가서 구운 빵을 꺼내 조리대로 다시 가져온 다음, 햄을
   올리고 나서 다시 넣어 둡니다
3. **작업 3**: 냉장고에 또 가서 햄 샌드위치를 꺼내 조리대로 다시 가져온 다음,
   치즈를 올리고 나서 다시 넣어 둡니다

GPU 용어로 보면 냉장고는 전역 메모리(HBM)이고, 조리대는 빠른 온칩
메모리(레지스터, 공유 메모리, 캐시)입니다. 핵심 문제는 HBM과 온칩 메모리
사이에서 데이터를 옮기는 비용이 연산 자체보다 훨씬 크다는 점입니다.

융합하지 않으면:

- 각 연산이 중간 결과를 전역 메모리에 다시 쓰는 경우가 많습니다
- 다음 연산이 그 결과를 다시 읽습니다
- 그 결과 메모리 왕복이 반복되고 대역폭 압박이 커집니다

융합하면:

- 여러 연산이 커널 하나로 합쳐집니다
- 중간 결과를 빠른 온칩 메모리에 둘 수 있는 경우가 많습니다
- 불필요한 전역 메모리 읽기/쓰기를 피합니다
