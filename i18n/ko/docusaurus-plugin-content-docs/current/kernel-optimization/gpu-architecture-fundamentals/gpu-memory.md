# GPU 메모리 계층(memory hierarchy)

GPU 메모리는 계층 구조로 구성됩니다. 작은 온칩(on-chip) 저장 공간은 연산 유닛
가까이에 있어 지연 시간이 짧고, 고대역폭 메모리(high bandwidth memory, HBM)는 칩
바깥에서 훨씬 큰 용량을 제공합니다. 대부분의
[GPU 커널 최적화 기법](/kernel-optimization/kernel-optimization-for-llm-inference/)은
결국 데이터를 덜 옮기거나, 이 계층의 더 빠른 단계에서 데이터를 재사용하는
방법으로 귀결됩니다.

계층을 한 단계 내려갈 때마다 용량은 늘어나지만 데이터는 연산 유닛에서 더
멀어집니다. 아래에서 단계를 하나 선택하면 물리적 위치에 따라 같은 데이터를
재사용할 수 있는 그룹이 어떻게 달라지는지 볼 수 있습니다.

## 레지스터 {#registers}

레지스터는 GPU에서 가장 빠른 저장 공간입니다. 각 스레드는 논리적으로 자신만의
레지스터 집합을 가지며, 다른 스레드는 여기에 접근할 수 없습니다. 하지만
물리적으로 이 레지스터들은
[SM](/kernel-optimization/gpu-architecture-fundamentals/streaming-multiprocessors/)에
있는 큰 레지스터 파일(예: H100에서는 SM당 256 KB)에서 나옵니다. 이 레지스터
파일은 SM에 상주하는 모든 스레드가 함께 쓰며, 스레드들에게 나누어 할당됩니다.

레지스터 접근은 공유 메모리나 HBM에 접근하는 것보다 훨씬 저렴합니다. 데이터가
이미 칩 위에 있고 연산 유닛이 바로 사용할 수 있기 때문입니다.

레지스터는 한정된 자원입니다. 레지스터 할당이 제약 조건이 되는 상황에서는
스레드당 레지스터 사용량이 늘어나면 상주할 수 있는 스레드와 워프 수가 줄어들 수
있습니다. 이것이 점유율 트레이드오프의 주된 원인입니다.

## 공유 메모리(SMEM)와 L1 캐시 {#shared-memory-smem-and-l1-cache}

최신 GPU는 각 SM 안에 빠른 온칩 메모리 두 종류를 제공합니다. 바로 공유
메모리(shared memory, SMEM)와 L1 캐시입니다. 둘은 같은 물리적 SRAM을 사용하는
경우가 많지만 역할은 다릅니다.

L1 캐시는 하드웨어가 관리합니다. 스레드가 전역 메모리(HBM)에서 데이터를 읽으면
GPU가 그 데이터를 자동으로 L1에 저장할 수 있습니다. 같은 데이터에 다시 접근하면
HBM까지 가지 않고 L1에서 훨씬 빠르게 가져올 수 있습니다(캐시 적중). 이 과정은
프로그래머에게 드러나지 않습니다. 프로그래머가 데이터를 L1에 직접 올리거나
무엇이 L1에 남을지 제어하지 않습니다. 따라서 L1은 메모리 접근 패턴에 시간적 또는
공간적 지역성(locality)이 있을 때 성능을 높여 주는 최선 노력(best-effort) 방식의
최적화로 보는 것이 좋습니다.

반면 공유 메모리는 프로그래머가 관리합니다. 공유 메모리는 명시적으로 할당하는
작은 메모리 공간이며, 한 스레드 블록 안의 모든 스레드가 함께 사용합니다.
스레드들은 공유 메모리를 직접 읽고 쓸 수 있고, 동기화(예: `__syncthreads()`)로
접근을 조율합니다. 그래서 공유 메모리는 스레드 간 협업을 위한, 예측 가능하고
제어 가능한 작업 공간이 됩니다.

공유 메모리의 주된 목적은 비용이 큰 HBM 접근을 줄이는 것입니다. 흔한 패턴은
데이터를 전역 메모리에서 공유 메모리로 한 번 읽어 온 뒤, 여러 스레드가 여러 번
재사용하는 것입니다. 공유 메모리는 칩 위에 있고 HBM보다 훨씬 빠르기 때문에 이
방식으로 성능을 크게 높일 수 있습니다. 이 패턴은
[행렬 곱](/kernel-optimization/gpu-architecture-fundamentals/tensor-cores/)과
[어텐션](/kernel-optimization/flashattention/)을 비롯한 많은 고성능 커널에서 볼
수 있습니다.

공유 메모리는 뱅크(bank) 단위로 구성됩니다(일반적으로 32개). 한
[워프](/kernel-optimization/gpu-architecture-fundamentals/threads-warps-blocks/#warps)
안의 여러 스레드가 같은 뱅크의 서로 다른 주소에 동시에 접근하면 뱅크 충돌(bank
conflict)이 발생하고, 접근이 직렬화됩니다(같은 주소를 읽는 스레드들은
브로드캐스트로 처리되므로 충돌하지 않습니다). 뱅크 충돌을 피하는 것은 커널
튜닝에서 흔히 쓰는 미세 최적화입니다.

두 메모리를 비교하면 다음과 같습니다.

|             | 공유 메모리                | L1 캐시                           |
|-------------|----------------------------|-----------------------------------|
| 관리 주체   | 프로그래머                 | 하드웨어                          |
| 범위        | 스레드 블록                | SM 단위(SM에 있는 모든 블록)      |
| 유지 기간   | 블록 수명 동안             | 하드웨어가 축출                   |
| 뱅크 충돌   | 발생 가능                  | 없음(하드웨어가 처리)             |
| 적합한 경우 | 미리 계획할 수 있는 재사용 | 불규칙하거나 예측하기 어려운 접근 |

흔히 나오는 질문이 있습니다. 이미 레지스터가 있는데 왜 공유 메모리(SMEM)와 L1
캐시가 필요할까요?

레지스터는 GPU에서 가장 빠른 저장 공간이지만, 레지스터만으로는 충분하지
않습니다.

1. **레지스터는 스레드 전용입니다**. 한 스레드는 다른 스레드에 할당된 레지스터를
   직접 읽을 수 없습니다. 워프 셔플(warp shuffle) 명령어로 한 워프 안에서
   레지스터 값을 교환할 수는 있고, 공유 메모리를 사용하면 스레드 블록 전체에서
   데이터를 재사용할 수 있습니다. L1은 반복되는 접근이 HBM까지 가지 않도록 막아
   주기도 합니다.
2. **레지스터는 한정되어 있습니다**. 각 스레드는 적은 수의 레지스터만 받습니다.
   전체 가중치 텐서나 큰 타일 같은 큰 데이터는 레지스터에 들어가지 않으므로
   메모리에서 가져와야 합니다. L1은 이런 데이터를 자동으로 캐싱하는 데 도움이
   되고, 공유 메모리를 사용하면 데이터를 명시적으로 준비해 두고 재사용할 수
   있습니다.
3. **스레드 간 조율이 불가능합니다.** 스레드들은 레지스터로 서로 통신할 수
   없습니다. 공유 메모리는 협업과 동기화를 위한 공용 작업 공간을 제공합니다.

## L2 캐시 {#l2-cache}

L2 캐시는 가장 큰 온칩 메모리로, GPU의 모든 SM이 함께 사용하며 HBM으로 가기 전
마지막 빠른 경유지 역할을 합니다. H100의 L2 캐시는 약 50 MB이고, A100은 약 40
MB입니다.

L2 캐시는 하드웨어가 관리합니다. 데이터를 L2에 직접 올리지 않습니다. 대신 L2가
최근의 전역 메모리 접근을 자동으로 캐싱합니다. 스레드 블록 사이에 어느 정도
데이터 재사용이 있는 워크로드라면 L2가 HBM 트래픽을 크게 줄일 수 있습니다.

L1 캐시와 공유 메모리는 SM 하나 안에서 동작하는 반면, L2는 SM 사이와 스레드 블록
사이의 재사용을 잡아내기 위해 존재합니다. 온칩 메모리에 들어가지 않는 데이터나
여러 블록이 접근하는 데이터도 HBM에서 반복해서 가져오지 않고 L2를 통해 재사용할
수 있습니다.

LLM 추론에서 L2 캐시는 다음과 같은 경우에 도움이 됩니다.

- 그룹 쿼리 어텐션(grouped-query attention)이나 멀티 쿼리 어텐션(multi-query
  attention)에서 여러 쿼리 헤드가 공유하는 KV 캐시 항목
- 배치 원소 사이에서 재사용되는 가중치 타일
- 작은 룩업 테이블이나 메타데이터

하지만 작업 집합(working set)이 매우 크면(LLM 추론에서는 흔한 일입니다) L2
적중률이 떨어지고 HBM 대역폭이 제약 조건이 됩니다.

## HBM(고대역폭 메모리) {#hbm-high-bandwidth-memory}

HBM은 GPU의 주 메모리입니다(흔히 VRAM 또는 전역 메모리라고 부릅니다). 모델
가중치, KV 캐시, 활성화 값을 비롯한 모든 대형 데이터 구조가 HBM에 저장됩니다.
최신 데이터센터 GPU는 HBM2e, HBM3, HBM3e를 사용합니다.

| GPU             | HBM 용량 | 최대 HBM 대역폭 |
|-----------------|---------:|----------------:|
| NVIDIA A100 SXM |    80 GB |        2.0 TB/s |
| NVIDIA H100 SXM |    80 GB |       3.35 TB/s |
| NVIDIA H200 SXM |   141 GB |        4.8 TB/s |

LLM 추론에서는 다음과 같습니다.

- HBM 용량은 GPU 하나에 모델 상태와 KV 캐시를 얼마나 올려 둘 수 있는지를
  결정합니다.
- HBM 대역폭은 디코드 단계의 토큰 처리량을 결정하는 경우가 많습니다.

HBM은 용량이 크지만 온칩 메모리에 비해 느립니다. HBM 접근 한 번에 수백 사이클이
걸립니다. 그래서 커널 최적화는 HBM과 연산 유닛 사이의 트래픽을 최소화하는 데
집중합니다.

## 메모리 병합 {#memory-coalescing}

메모리 병합(memory coalescing)은 한 워프의 메모리 요청이 하드웨어 메모리
트랜잭션에 얼마나 효율적으로 들어맞는지를 나타냅니다. 워프는 로드 명령어 하나를
실행하지만, GPU는 요청된 값을 하나씩 별도의 연산으로 가져오지 않습니다. 대신
활성 스레드 전체의 주소를 묶어, 고정 크기의 메모리 영역을 담당하는 트랜잭션으로
만듭니다.

현재 NVIDIA GPU에서 전역 메모리 로드는 32바이트 섹터(sector) 단위로 처리됩니다.
한 명령어에 필요한 섹터 수가 적을수록 접근이 더 잘 병합된 것입니다.

:::note
섹터는 NVIDIA GPU가 전역 메모리 로드의 전송 단위로 사용하는, 32바이트로 정렬된
메모리 영역입니다. 스레드에 4바이트만 필요하더라도 GPU는 그 바이트가 들어 있는
32바이트 섹터 전체를 가져올 수 있습니다.
:::

한 워프의 스레드 32개가 모두 `float32` 값 하나, 즉 스레드당 4바이트를 로드한다고
가정해 보겠습니다. 워프는 총 128바이트를 요청합니다.

```text
32 threads × 4 bytes = 128 bytes
```

인접한 스레드가 인접한 원소를 읽으면, 주소들은 인접한 32바이트 섹터 4개에 들어갈
수 있습니다.

```text
Thread 0  → bytes 0–3
Thread 1  → bytes 4–7
Thread 2  → bytes 8–11
...
Thread 31 → bytes 124–127
```

GPU는 128바이트를 가져오고, 워프는 128바이트를 모두 사용합니다. 첫 주소가 적절히
정렬되어 있다면, 이런 접근이 완전히 병합된 접근입니다.

이번에는 스트라이드가 커서 모든 스레드가 서로 다른 32바이트 섹터에서 읽는 경우를
생각해 보겠습니다. 워프가 요청하는 유용한 데이터는 여전히 128바이트뿐이지만,
GPU는 이 로드를 처리하기 위해 섹터 32개가 필요할 수 있습니다.

```text
32 sectors × 32 bytes = 1,024 bytes fetched
```

전송된 데이터 중 그 명령어에 유용한 것은 8분의 1뿐입니다. 나머지 바이트는 워프에
아무 값도 제공하지 않으면서 대역폭만 소모합니다. 이후 접근에서는 캐시가 도움이
될 수 있지만, 원래의 주소 패턴을 병합된 패턴으로 바꾸어 주지는 않습니다.

좋은 병합은 대개 인접한 스레드를 인접한 텐서 원소에 대응시키는 데서 나옵니다.
정렬도 중요합니다. 연속된 128바이트 요청이라도 섹터 경계를 넘으면 트랜잭션이
하나 더 필요할 수 있습니다.

LLM 추론에서는 효율적인 메모리 접근이 특히 중요합니다. 많은 커널이 연산하는
양보다 훨씬 많은 데이터를 옮기기 때문입니다. 병합이 잘 되지 않으면 HBM 대역폭이
낭비되고, 산술 연산량이 같더라도 토큰 처리량이 떨어질 수 있습니다.

## 메모리 피라미드 {#the-memory-pyramid}

아래 값은 Hopper급 GPU의 대략적인 예시입니다. 정확한 용량, 지연 시간, 대역폭은
GPU, 접근 패턴, 측정 방법에 따라 다릅니다.

| 단계             | 크기(H100)                         | 대역폭        | 범위                          | 지연 시간     | 관리 주체                       |
|------------------|------------------------------------|---------------|-------------------------------|---------------|---------------------------------|
| 레지스터         | SM당 256 KB                        | 가장 높음     | 스레드 단위                   | ~1 사이클     | 컴파일러                        |
| 공유 메모리 / L1 | 통합 풀 256 KB, SMEM은 최대 228 KB | 실효 ~20 TB/s | 블록 단위(SMEM) / SM 단위(L1) | ~20-30 사이클 | 프로그래머(SMEM) / 하드웨어(L1) |
| L2 캐시          | 50 MB                              | ~12 TB/s      | 모든 SM                       | ~200 사이클   | 하드웨어                        |
| HBM              | 80 GB                              | 3.35 TB/s     | 전역                          | ~400+ 사이클  | 프로그래머 / 런타임             |

타일링(tiling), 융합(fusion), 데이터 레이아웃 변경을 비롯한 많은 커널 최적화
기법은 자주 쓰는 데이터를 HBM에서 반복해서 읽지 않고 레지스터나 공유 메모리에
유지합니다. 이렇게 해서 피라미드 아래쪽의 트래픽을 줄입니다.
