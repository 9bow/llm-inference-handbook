# LLM 추론 매개변수(inference parameters)

추론 매개변수(inference parameter)는 LLM 요청과 함께 전달하는 설정으로, 모델이
응답을 생성하는 방식을 제어합니다. 추론 매개변수는 모델 가중치를 바꾸지
않습니다. 대신
[디코딩 과정](/llm-inference-basics/how-does-llm-inference-work/)에 영향을
줍니다. 예를 들면 다음과 같습니다.

- 다음 토큰을 어떻게 선택할지
- 모델이 얼마나 길게 생성을 이어갈 수 있는지
- 언제 멈춰야 하는지
- 반복을 어느 정도까지 허용할지

일부 매개변수는 주로 출력의 품질과 스타일에 영향을 줍니다. 반면 스케줄링,
[처리량](/llm-inference-basics/llm-inference-metrics/), 메모리 사용량, 프로덕션
비용 등 서빙에 직접 영향을 주는 매개변수도 있습니다.

## 자주 쓰는 추론 매개변수 {#common-inference-parameters}

이 매개변수들은 호스팅 API,
[OpenAI 호환 서버](/model-interaction/openai-compatible-api/), vLLM, SGLang, MAX
같은
[추론 프레임워크](/getting-started/choosing-the-right-inference-framework/),
에이전트 프레임워크에서 볼 수 있습니다. 자주 쓰는 매개변수를 간단히 정리하면
다음과 같습니다.

| 매개변수                  | 제어 대상                                           | 주요 용도                                             |
|---------------------------|-----------------------------------------------------|-------------------------------------------------------|
| `temperature`             | 토큰 선택의 무작위성                                | 안정적인 답변에는 낮게, 창의적인 글쓰기에는 높게      |
| `top_p`                   | 샘플링 대상이 되는 누적 확률 질량                   | 가능성이 높은 토큰 집합으로 샘플링 범위를 제한        |
| `top_k`                   | 고려할 후보 토큰의 최대 개수                        | 순위가 매우 낮은 토큰 제거                            |
| `max_tokens`              | 출력 토큰의 최대 개수                               | 지연 시간과 비용의 상한 설정                          |
| `min_tokens`              | 출력 토큰의 최소 개수                               | 응답이 너무 일찍 끝나는 것을 방지                     |
| `stop` / `stop_token_ids` | 생성을 끝내는 텍스트 또는 토큰 패턴                 | 구분자, 섹션, 도구 경계 앞에서 정지                   |
| `presence_penalty`        | 이미 등장한 토큰에 페널티 부여                      | 새로운 주제나 표현을 유도                             |
| `frequency_penalty`       | 반복 빈도에 따라 토큰에 페널티 부여                 | 반복되는 단어나 구절 감소                             |
| `repetition_penalty`      | 반복되는 프롬프트 또는 출력 토큰에 페널티 부여      | 오픈소스 서빙 스택에서 흔히 사용                      |
| `seed`                    | 샘플링에 쓰는 난수 시드                             | 테스트 중 재현성 향상                                 |
| `logprobs`                | 토큰 확률 상세 정보                                 | 출력 디버깅, 점수 매기기, 검사                        |
| `n` / `best_of`           | 후보 출력의 개수                                    | 비용을 더 들여 여러 대안을 생성                       |

모든 공급자가 모든 필드를 지원하지는 않으며, 정확한 이름도 다를 수 있습니다.
필드 이름이 같더라도 모델과 프레임워크에 따라 동작이 다를 수 있습니다. 이러한
설정은 어디서나 똑같이 동작한다고 보장되는 값이 아니라, 평가 대상의 일부로
다뤄야 합니다.

## 온도 {#temperature}

`temperature`는 샘플링 전에 모델이 가능성이 높은 토큰과 낮은 토큰에 확률을
얼마나 고르게 분산할지 제어합니다.

온도를 낮추면 확률 분포가 더 뾰족해집니다. 즉, 모델이 확률이 가장 높은 토큰을
고를 가능성이 커지므로 출력이 더 안정적이고 예측 가능해집니다.

온도를 높이면 분포가 평평해집니다. 가능성이 낮은 토큰도 등장할 기회가
늘어나므로, 출력이 더 다양하거나 의외이거나 창의적일 수 있습니다.

일반적인 패턴은 다음과 같습니다.

- 사실 기반 질의응답, 정보 추출, 분류,
  [구조화된 워크플로](/model-interaction/structured-outputs/)에는 낮은 온도를
  사용합니다.
- 어느 정도의 변화를 허용할 수 있다면 채팅, 요약, 제품 문구에는 중간 정도의
  온도를 사용합니다.
- 브레인스토밍, 소설, 이름 짓기 등 창의적인 작업에는 더 높은 온도를 사용합니다.
- 탐욕적 디코딩(greedy decoding)이나 거의 결정론적인 디코딩을 원한다면
  `temperature: 0` 또는 0에 가까운 값을 사용합니다.

낮은 온도가 사실 정확성을 보장하지는 않습니다. 낮은 온도는 디코드 단계의
무작위성만 줄여 줍니다. [프롬프트](/model-interaction/prompt-engineering/)에
근거가 부족하거나, 모델에 지식이 없거나, 애플리케이션이 출력을 검증하지 않으면
모델은 여전히 확신에 찬 오답을 낼 수 있습니다.

## Top-p 샘플링과 top-k 샘플링 {#top-p-and-top-k-sampling}

`top_p`와 `top_k`는 샘플링 전에 선택 대상이 될 수 있는 토큰을 제한합니다.

### Top-p {#top-p}

`top_p`는 뉴클리어스 샘플링(nucleus sampling)이라고도 하며, 누적 확률이 임곗값에
도달하는 가장 작은 토큰 집합만 남깁니다. 예를 들어 `top_p: 0.9`는 샘플러가 확률
질량의 약 90%를 함께 차지하는, 가능성이 가장 높은 토큰들만 고려한다는 뜻입니다.

이 방식은 모델의 불확실성에 맞춰 조정됩니다. 다음 토큰이 명확하면 후보 집합이
작을 수 있습니다. 그럴듯한 토큰이 많으면 집합이 커집니다.

### Top-k {#top-k}

`top_k`는 가능성이 가장 높은 `k`개의 토큰만 남깁니다. 예를 들어 `top_k: 50`은
모델이 상위 50개 후보에서 샘플링하고 그 아래의 토큰은 모두 무시한다는 뜻입니다.

이 방식은 단순하고 예측 가능하지만, 확률 분포의 모양에 맞춰 조정되지는 않습니다.
상위 50개 토큰에 약한 선택지가 너무 많이 들어 있을 때도 있습니다. 반대로 적절한
선택지가 50개보다 많을 때도 있습니다.

아래 시각화 도구는 같은 분포에 두 필터를 각각 적용한 결과를 보여 줍니다. 뾰족한
분포, 혼합된 분포, 평평한 분포 사이를 전환해 보세요. 답 하나가 압도적이면
top-p는 더 적은 토큰을 남기고, 그럴듯한 답이 많으면 더 많은 토큰을 남깁니다.
Top-k는 분포 모양과 관계없이 항상 같은 개수를 남깁니다.

### 어떤 매개변수를 조정해야 할까 {#which-one-should-you-tune}

많은 시스템에서 `temperature`, `top_p`, `top_k`를 함께 사용할 수 있습니다. 함께
쓰면 유용할 수 있지만, 동작을 이해하고 예측하기는 더 어려워집니다.

실용적인 출발점은 다음과 같습니다.

- `temperature`를 먼저 조정합니다.
- 모델이 각 단계에서 확률이 가장 높은 토큰을 선택하게 하려면
  [탐욕적 디코딩](/llm-inference-basics/how-does-llm-inference-work/#how-are-tokens-selected-via-sampling)을
  사용합니다. 서빙 구성이 고정되어 있다면 결정론적으로 동작하지만, 반복에 빠지기
  쉽습니다.
- 긴 꼬리를 잘라 내면서 샘플링을 적응적으로 유지하려면 `top_p`를 사용합니다.
- 추론 프레임워크나 모델 계열이 권장하는 경우, 또는 후보 토큰 수에 엄격한 상한이
  필요한 경우에는 `top_k`를 사용합니다.
- `top_k`와 `top_p`를 함께 사용합니다. 많은 샘플러에서는 top-k가 먼저 순위가
  낮은 꼬리를 제거하고, 이어서 top-p가 후보 집합을 한 번 더 좁힙니다.
- 평가 중에는 모든 매개변수를 한꺼번에 바꾸지 않습니다.

## 출력 길이 {#output-length}

LLM은 디코드 단계에서 토큰을 한 번에 하나씩 생성하므로, 길이 매개변수는
[지연 시간](/llm-inference-basics/llm-inference-metrics/)과 비용에 직접 영향을
줍니다.

`max_tokens`는 모델이 생성할 수 있는 토큰의 최대 개수를 설정합니다. 프로덕션에서
가장 중요한 제어 수단 가운데 하나입니다. 값이 너무 낮으면 응답이 중간에
잘립니다. 값이 너무 높으면 잘못된 프롬프트나 예외적인 입력이 GPU 시간을 낭비하고
꼬리 지연 시간을 늘릴 수 있습니다.

`min_tokens`는 모델이 멈추기 전에 최소한 일정 개수의 토큰을 생성하도록
요구합니다. 신중하게 사용해야 합니다. 비어 있거나 지나치게 짧은 응답을 막는 데
도움이 되지만, 답이 자연스럽게 끝난 뒤에도 모델이 계속 글을 쓰게 만들 수
있습니다.

적절한 기본값은 애플리케이션에 따라 다릅니다.

- **짧은 분류나 정보 추출**: 작은 `max_tokens`. 보통 100 미만입니다.
- **고객 지원 답변**: 완전한 답변을 쓸 만큼 충분하되, 장황해지지 않도록 상한을
  둡니다.
- **코드 생성이나 긴 글 작성**: 더 큰 상한을 두고, 지연 시간과 비용을 더 철저히
  모니터링합니다.
- **배치 작업**: 잘못된 입력 하나가 전체 실행을 좌우하지 않도록 길이 상한을
  명시합니다.

추론 시스템에서는 출력 길이가 스케줄링에도 영향을 줍니다. 생성이 길어지면 활성
요청 상태를 더 오래 유지하고,
[KV 캐시](/llm-inference-basics/how-does-llm-inference-work/#prefill)를 더 오래
점유하며, 지연 시간에 민감한 트래픽을 방해할 수 있습니다.

## 정지 시퀀스 {#stop-sequences}

정지 시퀀스(stop sequence)는 특정 텍스트가 나타나면 생성을 끝내라고 서버에 알려
줍니다. 일부 API는 `stop` 같은 문자열 기반 정지를 사용하고, 저수준 엔진은
`stop_token_ids` 같은 토큰 ID도 지원할 수 있습니다.

정지 시퀀스는 출력의 경계가 명확할 때 유용합니다.

- 채팅 기록 형식에서는 `"\n\nUser:"`에서 정지합니다.
- 구조화된 프롬프트에서는 `"</json>"`이나 다른 구분자에서 정지합니다.
- 목록 항목 하나, SQL 문 하나, [도구 호출](/model-interaction/function-calling/)
  하나가 끝나면 정지합니다.

정지 시퀀스가 스키마 강제를 대신하지는 않습니다. 정지 시퀀스는 특정 시퀀스가
나타났을 때 생성을 끝낼 뿐입니다. JSON 형식을 보장해야 한다면, 공급자가 지원하는
경우 [구조화된 출력](/model-interaction/structured-outputs/)이나 제약 디코딩을
사용하세요.

흔한 부분 문자열은 주의해야 합니다. 일반적인 내용 안에 등장하는 정지 시퀀스는
올바른 답변을 중간에 잘라 버릴 수 있습니다.

## 반복 페널티 {#repetition-penalties}

페널티 매개변수는 이미 등장한 내용을 바탕으로 토큰 점수를 조정합니다. 루프나
반복적인 표현을 줄이는 데 실용적인 도구입니다.

- `presence_penalty`는 한 번이라도 등장한 토큰에 페널티를 줍니다. 값이 높을수록
  모델이 새로운 토큰이나 주제를 꺼내도록 유도합니다.
- `frequency_penalty`는 토큰이 자주 등장할수록 더 큰 페널티를 줍니다. 모델이
  같은 단어나 구절을 너무 많이 반복할 때 유용합니다.
- `repetition_penalty`는 프롬프트나 생성된 텍스트에 등장한 토큰에 페널티를
  줍니다. 보통 `1`보다 큰 값은 반복을 억제하고, `1`보다 작은 값은 반복을
  부추깁니다.

이 매개변수들이 도움이 될 수는 있지만, 정교한 도구는 아닙니다. 프롬프트가
모호하거나, 컨텍스트에 잡음이 많거나, 작업 자체가 반복적인 출력을 요구해서
모델이 반복하는 경우라면, 페널티는 증상을 가릴 뿐일 수 있습니다. 페널티가
지나치면 모델이 정당하게 반복해야 하는 용어까지 피하게 되어 글이 어색해질 수도
있습니다.

## 여러 후보 생성 {#multiple-candidates}

일부 API는 프롬프트 하나에 대해 여러 개의 완성 결과를 반환할 수 있습니다.

`n`은 보통 반환할 출력의 개수를 뜻합니다. `best_of`는 보통 가장 좋은 `n`개를
반환하기 전에 내부적으로 생성할 후보의 개수를 뜻합니다.

창의적인 선택지가 여러 개 필요하거나 다른 시스템이 후보에 점수를 매길 때 도움이
될 수 있습니다. 대신 비용이 듭니다. 후보 다섯 개를 요청하면 시스템의 생성
작업량이 거의 다섯 배가 될 수 있습니다. `best_of`는 끝내 반환되지 않는 후보까지
생성할 수 있으므로 비용이 더 클 수 있습니다.

이 매개변수들은 목적을 분명히 하고 사용하세요.

- **적합한 경우**: 브레인스토밍, 재순위화, 테스트 시점 선택, 평가 데이터 생성
- **부적합한 경우**: 추가 토큰 하나하나가 중요한 대량의 프로덕션 요청
- **위험한 경우**: 지연 시간에 민감한 채팅. 후보 생성이 꼬리 지연 시간을 늘릴 수
  있습니다.

## 재현성과 로그 확률 {#reproducibility-and-log-probabilities}

LLM 샘플링에는 무작위성이 있습니다. 앞에서 설명했듯이, 모델은 각 단계에서
`temperature`, `top_p` 같은 매개변수를 바탕으로 다음 토큰을 확률적으로 고릅니다.
`seed`는 이 샘플링을 구동하는 난수 생성기를 초기화합니다. 같은 `seed`, 동일한
입력, 동일한 매개변수, 안정적인 서빙 구성이 갖춰지면 같거나 거의 같은 출력을
얻는 경우가 많습니다. 이는 프롬프트를 테스트하거나, 모델 버전을 비교하거나,
예상치 못한 출력을 디버깅할 때 유용합니다.

하지만 시드를 프로덕션에서 완벽하게 보장되는 수단으로 여기지는 마세요. 모델
버전, 토크나이저, 서빙 프레임워크, 하드웨어 커널, 배칭 동작, 부동소수점 구현이
바뀌면 재현성도 달라질 수 있습니다.

`logprobs`는 생성된 토큰의 확률 정보를 반환합니다. 일부 시스템은 프롬프트 토큰의
확률 정보를 알려 주는 `prompt_logprobs`도 지원합니다.

이 필드들은 다음과 같은 경우에 유용합니다.

- 모델이 특정 토큰을 고른 이유를 살펴볼 때
- 신뢰도 휴리스틱을 만들 때
- 후보 완성 결과를 비교할 때
- 분류 프롬프트를 디버깅할 때
- 제한된 레이블을 모델이 얼마나 강하게 선호하는지 측정할 때

이 필드들은 응답 크기를 늘릴 수 있고, 채팅 API에서 항상 지원되지는 않습니다.
모든 프로덕션 요청에 기본으로 켜지 말고, 그 신호가 필요할 때 활성화하세요.

## 고급 제어 {#advanced-controls}

한 단계 더 나아간 추론 매개변수는 토큰 선택을 직접 제한하거나 변경할 수
있습니다. 자주 쓰이는 예는 다음과 같습니다.

- `logit_bias`는 특정 토큰의 점수를 높이거나 낮춥니다. 이렇게 특정 단어, 레이블,
  서식 표시를 더 쓰거나 덜 쓰도록 모델을 유도할 수 있습니다.
- `bad_words`는 특정 단어 시퀀스를 차단합니다.
- `allowed_token_ids`는 생성을 특정 토큰 집합으로 제한합니다. 이런 제어는
  강력하지만, 토큰화 결과가 사람이 보는 단어와 항상 일치하지는 않으므로 잘못
  쓰기 쉽습니다.

출력을 소프트웨어가 처리하는 경우에 고급 제어를 사용하세요. 예를 들어 정보 추출
파이프라인, [함수 호출](/model-interaction/function-calling/),
[구조화된 데이터 생성](/model-interaction/structured-outputs/)에는 보통 프롬프트
지시만으로는 얻을 수 없는 더 강한 보장이 필요합니다.

## 권장 출발점 {#recommended-starting-points}

모든 경우에 가장 좋은 매개변수 구성은 없습니다. 적절한 기본값은 작업, 모델 계열,
서빙 스택에 따라 다릅니다. 같은 설정이라도 모델에 따라 동작이 크게 다를 수
있습니다.

그래도 다음 범위는 평가를 시작할 때 유용한 출발점입니다.

| 사용 사례                       | 온도        | Top-p      | max_tokens          | 참고                                                              |
|---------------------------------|-------------|------------|---------------------|-------------------------------------------------------------------|
| 분류                            | `0.0–0.2`   | `1.0`      | 작게, 보통 `< 20`   | 결정론적 출력을 선호                                              |
| 정보 추출 / 구조화된 구문 분석  | `0.0–0.2`   | `1.0`      | 작게                | 변동과 서식 이탈을 최소화                                         |
| RAG / 사실 기반 QA              | `0.1–0.5`   | `0.9–1.0`  | 중간                | 무작위성을 낮추면 환각이 줄어들 수 있음                           |
| 범용 채팅 어시스턴트            | `0.5–0.8`   | `0.9–1.0`  | 중간                | 안정성과 다양성의 균형                                            |
| 요약                            | `0.2–0.7`   | `0.9–1.0`  | 중간                | 요약을 얼마나 추출적으로 또는 창의적으로 만들지에 따라 다름       |
| 코드 생성                       | `0.0–0.3`   | `1.0`      | 중간에서 크게       | 온도를 낮추면 보통 구문 안정성이 높아짐                           |
| 브레인스토밍 / 아이디어 발상    | `0.7–1.2`   | `0.9–0.95` | 중간에서 크게       | 더 다양한 출력을 유도                                             |
| 창작 글쓰기                     | `0.8–1.3`   | `0.9–0.95` | 크게                | 다양성이 높지만 불안정성도 높음                                   |

이 값들은 출발점일 뿐 규칙이 아닙니다. 매개변수는 항상 실제 프롬프트, 모델 버전,
워크로드로 평가하세요.

프로덕션 시스템에서는 매개변수 조정이 인프라 문제이기도 합니다. 예를 들어 출력
길이가 길어지고 샘플링이 더 탐색적이 되면, 부하가 걸린 상태에서
[지연 시간](/llm-inference-basics/llm-inference-metrics/), GPU 사용률, KV 캐시
부담, 꼬리 지연 시간이 늘어날 수 있습니다.

## 자주 묻는 질문 {#faqs}

### 추론 매개변수는 모델 하이퍼파라미터와 같은가요? {#are-inference-parameters-the-same-as-model-hyperparameters}

아닙니다. 하이퍼파라미터는 보통 학습률이나 배치 크기처럼 학습 중에 쓰는 설정을
가리킵니다. 추론 매개변수는 이미 학습된 모델에서 출력을 생성할 때 쓰는, 요청
시점의 설정입니다.

### 출력이 왜 일찍 끝났나요? {#why-did-my-output-stop-early}

흔한 원인으로는 낮은 `max_tokens`, 일반 텍스트 안에 등장한 정지 시퀀스, 모델이
생성한 시퀀스 종료 토큰(EOS), 공급자 측의 안전 제한이나 길이 제한이 있습니다.

### 모든 모델이 같은 매개변수를 지원하나요? {#do-all-models-support-the-same-parameters}

아닙니다. 호스팅 공급자, OpenAI 호환 서버, 오픈소스 엔진은 각기 다른 매개변수
하위 집합을 제공합니다. 서빙 스택에 따라 일부 매개변수는 무시되거나, 거부되거나,
다르게 구현될 수 있습니다.
