# 에이전트 하네스

에이전트 하네스(agent harness)는 하나 이상의 AI 모델을 감싸서, 모델이 사용자 및
주변 환경과 상호작용할 수 있게 해 주는 시스템입니다. 하네스는 모델과 오래
이어지는 대화를 유지할 수 있고, 모델이 요청하면 다른 프로그램으로 작업을 실행할
수 있습니다.

하네스는 대화 상태를 유지하고, 사용 가능한 도구를 노출하고, 승인된 작업을
실행하고, 관찰 결과를 돌려주고, 모델에 다시 프롬프트를 보낼지 멈출지를
결정합니다. 이 작업은 보통 반복적인 제어 루프 안에서 이루어집니다. 가중치가
바뀌지 않으므로 하네스가 모델의 능력 자체를 높이지는 않습니다. 대신 모델에
환경에 관한 정보를 제공해서, 유용한 작업이 안전하고 반복적으로 이루어지게
합니다. 이 관계는 흔히 다음과 같이 요약합니다.

> 에이전트 = 모델 + 하네스

## 에이전트 하네스가 필요한 이유 {#why-do-you-need-an-agent-harness}

오늘날 많은 모델은 텍스트뿐 아니라 이미지, 오디오, 비디오도 입력으로 받습니다.
하지만 주변 애플리케이션의 지원이 없으면 모델은 도구를 실행하거나, 코드를
실행하거나, 환경을 구성하거나, API 호출 사이에 상태를 유지하거나, 더 큰 작업이
끝났는지 확인할 수 없습니다.

[함수 호출](/model-interaction/function-calling/)은 모델이 작업을 요청할 수 있게
해서 이 공백의 일부를 메웁니다. 하지만 요청은 실행이 아닙니다.
[모델 컨텍스트 프로토콜(Model Context Protocol, MCP)](/model-interaction/model-context-protocol/)은
도구와 데이터 소스를 연결하는 방식을 표준화하지만, 에이전트 루프는 정의하지
않습니다. 도구를 실행하고, 결과를 다시 전달하고, 계속할지 멈출지를 결정하는
무언가가 여전히 필요합니다.

하네스를 신중하게 설계하지 않으면 모델은 예측 가능한 방식으로 실패합니다.

- **끝없는 루프**. 진전 없이 같은 작업을 반복하거나 수정만 계속합니다.
- **컨텍스트 과부하**. 로그, 파일, 도구 결과가 정작 중요한 지시를 밀어냅니다.
- **안전하지 않은 작업**. 형식상 올바른 도구 호출이 모델이 직접 권한을 가져서는
  안 되는 시스템에 도달합니다.
- **거짓 완료**. 결과를 확인하는 테스트나 외부 검사 없이 성공했다고 보고합니다.
- **취약한 복구**. 체크포인트나 재시도 정책이 없어서 타임아웃이나 잘못된 형식의
  응답 하나로 작업이 끝나 버립니다.
- **불투명한 실패**. 답이 틀렸는데, 어떤 호출이나 도구 결과가 원인인지 보여 주는
  트레이스가 없습니다.

이는 주로 런타임 문제입니다. 더 강한 모델을 쓰면 일부 실수는 줄일 수 있지만,
모델을 업그레이드한다고 제어 흐름, 권한, 검증을 대신할 수는 없습니다.

## 에이전트 하네스 활용 사례 {#agent-harness-use-cases}

에이전트 하네스는 여러 번의 모델 호출, 외부 작업, 환경으로부터의 피드백이 필요한
작업에서 가장 효과적입니다. 흔한 활용 사례는 다음과 같습니다.

- **코딩 에이전트**. 저장소를 읽고, 파일을 편집하고, 테스트를 실행하고, 실패를
  바탕으로 반복 수정합니다. 하네스의 흔한 워크로드이면서 가장 까다로운 워크로드
  중 하나로, 큰
  [컨텍스트 윈도우](/llm-inference-basics/how-does-llm-inference-work/#what-is-a-context-window-and-how-does-it-work-in-llm-inference)와
  여러 단계에 걸친 도구 호출이 필요합니다.
- **심층 리서치**. 자료를 검색하고, 읽고, 교차 확인하고, 종합합니다. 이런 실행은
  오래 이어질 수 있고, 병렬 하위 에이전트(sub-agent)로 작업을 나눠 보낼 수
  있으며, 에이전트 자체의 추론보다 검색한 문서로 컨텍스트를 채웁니다.
- **고객 지원 서비스**. 지원 에이전트는 계정 데이터를 읽고, 정책을 적용하고,
  응답 초안을 작성하고, 환불이나 계정 변경 전에 승인을 요청할 수 있습니다.
- **브라우저 및 컴퓨터 사용**. 하네스는 도메인 제한과 확인 규칙을 적용하면서
  모델의 결정을 클릭이나 키 입력으로 바꿀 수 있습니다.
- **다중 에이전트 파이프라인**. 플래너가 전문화된 하위 에이전트에 작업을
  위임하고 그 결과를 병합합니다. 이는
  [다중 모델 추론 파이프라인](/infrastructure-and-operations/multi-model-inference-pipelines/)에서
  다룬 패턴의 에이전트 버전입니다.

## 널리 쓰이는 에이전트 하네스 {#popular-agent-harnesses}

하네스, 에이전트 프레임워크, 최종 사용자 제품 사이의 경계는 뚜렷하지 않습니다.
다음 프로젝트들은 순위가 아니라 대표적인 예시이며, 크게 두 그룹으로 나뉩니다.

### 코딩 에이전트 하네스 {#coding-agent-harnesses}

이 하네스들은 보통 작업 단위로 호출되고, 터미널이나 에디터에서 실행되며, 작업
범위를 저장소와 그 저장소를 빌드하고 테스트하는 데 필요한 명령으로 한정합니다.

- **Claude Code**. Anthropic의 하네스로, 터미널, IDE 통합, 데스크톱 클라이언트,
  웹에서 사용할 수 있고 MCP와 하위 에이전트를 지원합니다.
- **Codex**. OpenAI의 오픈소스 CLI는 샌드박스를 우선하는 터미널 하네스입니다.
  Codex는 IDE, 앱, 클라우드 워크플로에서도 실행됩니다.
- **OpenCode**. 공급자 선택, 권한, 전문화된 에이전트를 지원하는 오픈소스 터미널
  코딩 에이전트입니다.
- **Cline**. 에디터 확장으로 시작해 독립형 오픈소스 AI 코딩 에이전트로
  성장했으며, 병렬 에이전트와 SDK 워크플로를 지원합니다.
- **Letta Code**. 영구 메모리를 중심으로 만든 오픈소스, 모델 비종속
  하네스입니다. 에이전트는 매번 새로 시작하지 않고 세션 사이에 유지되며, 하위
  에이전트, 검색 가능한 대화 기록, 스킬을 지원합니다.

일부 모델 공급자는 Qwen Code, ZCode, Kimi Code처럼 자사 모델에 최적화된 하네스를
제공합니다.

### 범용 어시스턴트 하네스 {#general-purpose-assistant-harnesses}

이 하네스들은 작업 단위가 아니라 계속 실행되는 경우가 많습니다. 터미널 대신
메신저 앱으로 사용자에게 다가가고, 저장소 하나가 아니라 환경 전체(예: 이메일,
캘린더, 브라우저, 파일 시스템)에 걸쳐 작업합니다. 이렇게 범위가 넓다는 점이 곧
위험 요소입니다. 프롬프트 인젝션이나 악의적인 스킬 하나가 호스트에서 실제 작업을
일으키거나 민감한 데이터를 노출할 수 있습니다.

- **OpenClaw**. 사용자가 직접 관리하는 하드웨어에서 실행되는 오픈소스 개인
  어시스턴트입니다. 로컬 게이트웨이가 세션, 도구, 이벤트, 채널 연결을 위한
  컨트롤 플레인 역할을 합니다. 기본 에이전트는 필요에 따라 하위 에이전트를
  생성합니다. 플러그인과 스킬로 에이전트를 이메일, 브라우저 제어, 캘린더, 파일
  시스템 같은 여러 채널로 확장합니다.
- **Hermes Agent**. Nous Research의 오픈소스 셀프 호스팅 어시스턴트 하네스로,
  학습 루프를 중심으로 만들어졌습니다. 에이전트는 완료한 작업에서 스킬을 만들고,
  사용하면서 그 스킬을 다듬습니다. 선별된 메모리는 세션 사이에 유지됩니다.
  하나의 게이트웨이가 터미널 UI, Telegram, Discord, Slack, WhatsApp, Signal에
  걸쳐 하나의 대화를 이어 갑니다.

## 오픈소스 LLM으로 에이전트 하네스를 사용하는 방법 {#how-to-use-an-agent-harness-with-open-source-llms}

가장 잘 알려진 하네스들은 기본적으로 자신을 만든 벤더의 모델을 사용하도록
설정되어 있지만, 하네스와 모델은 분리할 수 있습니다. 많은 하네스는 로컬 또는
셀프 호스팅 추론 엔드포인트를 통해 오픈소스 모델이나 오픈 웨이트 모델에 연결할
수 있게 해 줍니다. 이렇게 하면 프라이버시와 커스터마이징 여지가 커지고, 비용을
관리하는 데도 도움이 됩니다.

API 호환성이 있으면 연결은 가능하지만, 프로토콜 호환성만으로 좋은 에이전트
동작이 보장되지는 않습니다. 하네스를 모델에 연결하고 그 조합이 제대로 동작하는지
확인하려면 다음 단계를 따르세요.

1. **도구 사용에 맞게 학습된 모델을 선택합니다**. 모델이 도구를 고르고, 올바른
   인자를 만들고, 도구 오류 후에 복구할 수 있는지 확인합니다.
2. **API 프로토콜을 맞춥니다**. 하네스에 따라
   [OpenAI 호환](/model-interaction/openai-compatible-api/) Chat Completions나
   Responses API, [Anthropic 호환](/model-interaction/anthropic-compatible-api/)
   Messages API, 또는 공급자 SDK가 필요할 수 있습니다.
3. **모델에 맞게 서버를 구성합니다**. 올바른 채팅 템플릿, 도구 호출 파서, 추론
   파서, 정지 토큰, 최대 컨텍스트 길이를 사용합니다.
4. **하네스가 엔드포인트를 가리키도록 설정합니다**. 기본 URL, 모델 이름, 필요한
   자격 증명(또는 자리 표시자)을 구성합니다. 대개는 MAX나 vLLM 같은
   [추론 프레임워크](/getting-started/choosing-the-right-inference-framework/)로
   서버를 시작하고, 하네스가 그 서버를 가리키도록 설정하면 됩니다.
5. **전체 루프를 테스트합니다**. 텍스트 품질만 보지 말고 도구 호출 정확도, 작업
   완료율, 복구, 컨텍스트 증가, 권한 관련 동작을 측정합니다.
6. **반복되는 프리픽스를 최적화합니다**. 변하지 않는 지시와 도구 정의를 프롬프트
   앞쪽에 두고, 프리픽스 캐시(prefix cache) 재사용을 모니터링합니다.

하네스에는 OpenAI 호환 API나 Anthropic 호환 API가 가장 쉬운 통합 경로인 경우가
많습니다. 일부 벤더 하네스는 다른 API나 더 넓은 API 범위를 요구하므로, 서버를
고르기 전에 최신 통합 문서를 확인하세요.

오픈 모델을 쓰면 용량 계획도 달라집니다. 긴 컨텍스트와 여러 개의 동시 에이전트
세션은 모델 가중치 크기로 짐작하는 것보다 더 많은 GPU 메모리를 사용할 수
있습니다. 프로덕션 한도를 정하기 전에 현실적인 실행 궤적(trajectory)과 도구
출력으로 테스트하세요.

## 자주 묻는 질문 {#faqs}

### 하네스 엔지니어링이란 무엇인가요? {#what-is-harness-engineering}

하네스 엔지니어링(harness engineering)은 모델 자체가 아니라 모델을 둘러싼
시스템을 바꿔서 에이전트의 결과를 개선하는 작업입니다. 여기에는 루프, 도구 정의,
매 턴 컨텍스트에 들어가는 내용, 중단 및 재시도 규칙, 검증 단계, 권한 경계가
포함됩니다. 하네스 엔지니어링은 이러한 요소를 측정하고 반복 개선하는 대상으로
다루며, 단일 응답의 품질이 아니라 실제 작업에서 종단 간으로 평가합니다. 같은
모델이라도 어떤 하네스에서 실행되느냐에 따라 같은 벤치마크에서 점수가 크게
달라질 수 있기 때문에 이 작업이 중요합니다.

### 에이전트 하네스와 에이전트 프레임워크는 어떻게 다른가요? {#what-is-the-difference-between-an-agent-harness-and-an-agent-framework}

하네스는 모델을 둘러싼 런타임 레이어입니다. 프레임워크는 그 레이어의 일부나
전부를 만드는 데 쓰는 소프트웨어 패키지입니다. 바로 쓸 수 있는 에이전트 제품은
하네스를 라이브러리로 노출하지 않으면서 하네스를 포함할 수 있습니다.

### 어떤 오픈소스 LLM이든 어떤 하네스와도 함께 쓸 수 있나요? {#can-any-open-source-llm-work-with-any-harness}

아닙니다. API 형식이 맞아야 하고, 모델이 하네스가 기대하는 도구 사용 동작을
갖춰야 합니다. 채팅 템플릿, 파서, 컨텍스트 한도, 추론 형식도 다를 수 있습니다.
호환되는 엔드포인트라고 해서 모든 모델을 서로 바꿔 쓸 수 있다고 가정하지 말고,
조합을 직접 테스트하세요.
